> # ⛔ 폐기 — 이 계획은 채택되지 않았다 (2026-08-15)
>
> **소유자 결정: `.type` 에 AST 를 넣지 않는다.**
>
> 이유는 [`260815-type-ast-proposal.md`](./260815-type-ast-proposal.md) 에 있다. 요약하면
> 타입은 **두 겹까지**다 — `Maybe<Array>` 이지 `Maybe<Array<number>>` 가 아니다. 안쪽 칸에는
> 이름 하나만 들어가고 재귀가 없으므로, 재귀 구조(AST)를 담을 자리 자체가 없다.
>
> **아래 본문의 숫자와 주장은 이 판정 이전 것이다.** 「227곳」·「82개 인스턴스」·재귀 검증·
> `extractors` 는 전부 무효다. 왜 이 길을 갔었는지가 다음 회차의 입력이라 지우지 않고 남긴다.

# 계획 — `.type` 을 문자열에서 타입 AST 로

## 무엇을 / 왜

**소유자 지적 (2026-08-14)** — *"`type` 에 array, Set, Map, Triple 등의 컨테이너 타입이
올 때 문제가 되는 거네요."*

그리고 설계 의도를 함께 밝혔다 — *"타입은 심볼로 정의하고 값은 문자열로 넣으려고 했습니다.
중첩 타입이라고 해도 이 형태가 결국 AST 가 될 거라고 예상했고요."*

**그 예상이 맞았다.** 지금 조립 키 14종을 **13줄짜리 파서 하나로 전부 파싱했다 — 실패 0.**

```
maybe(maybe(array))   → { name:'maybe',   args:[ { name:'maybe', args:[ { name:'array', args:[] } ] } ] }
either(string,number) → { name:'either',  args:[ {name:'string'}, {name:'number'} ] }
writert(maybe,array)  → { name:'writert', args:[ {name:'maybe'},  {name:'array'} ] }
```

**문자열 키가 이미 AST 다.** 남은 일은 새로 설계하는 것이 아니라 **직렬화된 것을 구조로
올리는 것**이다.

---

## 실측 — 문제의 크기

### 등록 인스턴스의 3분의 2가 컨테이너다

| 스칼라 — 태그가 값을 다 말한다 | 컨테이너 — 태그가 바깥만 말한다 |
| --- | --- |
| `function` 16 · `number` 12 · `boolean` 8 · `string` 8 · `any` 5 · `Date` 2 | `Array` **19** · `Maybe` 14 · `Either` 10 · `Object` 7 · `Task` 7 · `Validation` 5 · `Reader` 5 · `Writer` 5 · `State` 5 · `Free` 5 |
| **51개** | **82개** |

### 이미 터진 사례 — 튜플과 배열이 태그를 공유한다

`tests/staticland-spec.test.js` 머리에 **이미 기록돼 있다.**

```
Bifunctor tuple.bimap(x=>x*10, x=>x+1, [1,2]) → [10, 3]     둘째 자리만
Functor   array.map(x=>x*10, [1,2])           → [10, 20]    전부

둘의 .type: Array / Array   ← 같다
```

같은 값을 두 인스턴스가 다르게 보는데 태그가 같다. 그래서 명세 게이트 ③이 *"짝이 있는지만
보증하고 짝이 옳은지는 보증하지 않는다"* 고 자기 한계를 적어 뒀다.

### `Set`·`Map`·`Triple` 은 아예 못 넣는다

`Functor.lookup('set'|'map'|'tuple')` 셋 다 **없음**. 넣으려 해도 막힌다:

- `Set<number>` 와 `Set<string>` 을 태그 하나로 못 가른다.
- **`Map` 은 시작조차 안 된다** — 키와 값 **둘**인데 태그가 하나다.
- `Triple` 은 `[1,2,3]` 이 `'Array'` 다. **길이를 안 본다.**

### 두 체계는 서로 다른 것을 지킨다 — 겹치지 않는다

| | 무엇을 지키나 | 지점 |
| --- | --- | --- |
| 심볼 | **타입 클래스 인스턴스끼리의 관계** — `Ord` 가 진짜 `Setoid` 를 받았나 | **93곳** |
| 문자열 | **값이 이 인스턴스가 다루는 타입인가** | `types.of` 경유 **19곳** |

소유자 설계대로다. 이 계획은 **문자열 쪽만** 건드린다. 심볼은 그대로 둔다.

---

## 무엇을 만드나

### 노드는 하나면 된다

```javascript
type TypeAST = { name: string, args: TypeAST[] }
```

**`sanctuary-def` 는 `NULLARY`/`UNARY`/`BINARY`/`RECORD` 라는 종류 태그를 둔다**(실측:
소스에 상수로 선언돼 있다). 그건 그쪽이 구조가 아니라 **클래스**로 만들었기 때문이다.
구조로 두면 `args.length` 가 곧 항수라 종류 태그가 필요 없다.

| | 지금 | AST |
| --- | --- | --- |
| `number` | `'number'` | `{ name:'number', args:[] }` |
| `array(number)` | `'array(number)'` | `{ name:'array', args:[{name:'number',args:[]}] }` |
| `either(string,number)` | `'either(string,number)'` | `args` 가 둘 |
| **튜플** | `'Array'` — 배열과 같다 | `{ name:'tuple', args:[…] }` — **갈린다** |
| **`Map`** | **표현 불가** | `{ name:'map', args:[키, 값] }` |
| **`Triple`** | `'Array'` — 길이를 모른다 | `args.length === 3` |

### 파서와 직렬화

문자열 ↔ 구조를 오간다. **파서는 검증됐다 — 13줄로 14종 전부.** 직렬화는 그 역이다.
기존 문자열 키를 계속 쓰는 자리(레지스트리 조회, 에러 메시지)가 있으므로 둘 다 필요하다.

---

## 결정이 필요한 것 — 코드에서 답이 안 나온다

### ① `.type` 자리를 바꾸나, 옆에 두나 — **이것이 규모를 정한다**

| | (가) `.type` 을 AST 로 | (나) `.type` 은 두고 옆에 |
| --- | --- | --- |
| `index.js` `.type` 참조 | **35곳** | 0 |
| 생성자가 `type` 을 넘기는 자리 | **43곳** | 0 |
| `tests/` | **91곳** | 소수 |
| `types/*.d.ts` | **28곳** | 소수 |
| `docs/*.md` | **30곳** | 소수 |
| 조립 키 지점 | 14곳 | **14곳** |
| **합계** | **약 227곳** | **약 20곳** |
| 공개 표면 | **바뀐다** — `.type` 은 사용자도 읽는다 | 안 바뀐다 |
| 튜플/`Map`/`Triple` | **풀린다** | **안 풀린다** — 그것들은 `.type` 이 갈라야 한다 |

**(나)는 싸지만 이 계획의 목적을 못 이룬다.** 튜플과 배열을 가르려면 `.type` 자체가
갈려야 한다. (가)를 하되 **단계를 나눠** 한 번에 227곳을 건드리지 않는 길을 4단계에 적었다.

### ② 잎(leaf)은 지금 문자열 그대로인가

`'number'`·`'Array'`·`'Maybe'` 를 그대로 쓸지, 심볼이나 네임스페이스를 붙일지.
**지금 그대로 두기를 권한다** — 값의 표식(`_typeName`)과 짝이 맞아야 하고, 그것을 바꾸는
것은 별개의 파괴적 변경이다.

### ③ 레코드(`Setoid.Struct`)를 넣나

`{ age:'number', name:'string' }` 은 **필드 이름이 있어** 위치 인자로 안 된다.
`sanctuary-def` 는 `RECORD` 라는 별도 종류를 둔다. 다만 `Struct` 는 **지금 레지스트리
밖이라**(조회 키가 없다) 이번에 안 넣어도 된다.

### ④ "출신" 키를 AST 에 넣나 — **주의가 필요하다**

조립 키 14종의 괄호 안이 **전부 같은 뜻이 아니다.** 실측:

| 키 | 괄호 안이 가리키는 것 |
| --- | --- |
| `array(number)` `maybe(number)` `either(a,b)` | **원소 타입** ← 진짜 타입이다 |
| `plus(maybe)` | **어디서 유도했는지** |
| `const(array)` `forget(array)` | **무엇으로 모을지**(모노이드) |
| `statet(maybe)` `readert(maybe)` `eithert(task)` | **무엇 위에 쌓았는지**(모나드) |

`const(array).type` 이 `'Object'` 이고 `forget(array).type` 이 `'function'` 이다 —
**키와 타입이 아예 다른 것을 말한다.**

**뒤의 셋은 타입이 아니라 인스턴스의 출신이다.** AST 에 넣으면 `TypeAST` 가 두 가지 일을
하게 된다. **넣지 않기를 권한다** — 그것들은 지금처럼 문자열 레지스트리 키로 둔다.

## 단계 — 227곳을 한 번에 건드리지 않는다

| 단계 | 무엇 | 되돌릴 수 있나 |
| --- | --- | --- |
| 0 | 위 결정 ①~④ 확정 | — |
| 1 | 파서·직렬화·`TypeAST` 를 만들고 **아무도 안 쓴다**. 기존 14종 왕복(parse∘show ≡ id)을 테스트로 고정 | 쉬움 |
| 2 | `types.check` 가 AST 도 받게 한다. 문자열이 오면 파싱해서 처리 — **기존 43곳이 안 움직인다** | 쉬움 |
| 3 | 조립 인스턴스(14종)의 `.type` 을 AST 로. 여기서 **에러 메시지가 안쪽을 말하기 시작한다** | 보통 |
| 4 | 튜플을 `'Array'` 에서 갈라낸다 — `.type==='Array'` 인 **19개** 인스턴스가 영향권 | 어려움 |
| 5 | `Set`·`Map`·`Triple` 을 새로 넣는다 | 쉬움 (4단계가 있으면) |
| 6 | 문서·게이트 갱신 | 쉬움 |

**2단계가 핵심이다.** `types.check` 가 둘 다 받으면 나머지 43곳이 당장 안 움직여도 되고,
3~5단계를 하나씩 옮길 수 있다. 한 번에 다 바꾸는 것을 피하는 유일한 길이다.

**4단계가 가장 위험하다.** `.type==='Array'` 인 인스턴스가 19개이고 그중 `TupleBifunctor`
하나만 튜플이다. 나머지 18개가 배열이라는 것을 확인하고 옮겨야 한다.

## 완료 조건

1. 기존 조립 키 **14종**이 파싱→직렬화 왕복에서 **글자까지 같다.**
2. `types.check` 가 문자열과 AST 를 **둘 다** 받고, 기존 동작이 `npm run baseline` 차이 0.
3. `TupleBifunctor.bimap` 에 배열을 넣으면 **거부된다.** 지금은 통과한다.
4. `Map<string,number>` 인스턴스를 하나 만들어 등록하고 법칙이 돈다.
5. 조립 인스턴스의 에러 메시지가 안쪽을 말한다 — `must match array(number)`.
6. 뮤테이션: AST 를 잘못 파싱/직렬화하는 결함이 잡힌다.

---

## 이 계획이 **못 하는 것** — 미리 적는다

- **원소 타입 검사가 저절로 생기지 않는다.** `ArrayFunctor` 는 하나가 모든 배열을 받으므로
  그 태그는 여전히 `{ name:'array', args:[] }` 다. `map(f, [1,'a'])` 를 잡으려면
  `Functor.Array('number')` 같은 **인스턴스가 따로** 있어야 하고, 그것이 앞서 센 **82개**다.
  **AST 는 자리를 만들 뿐 인스턴스를 만들지 않는다.**
- **심볼 체계는 안 건드린다.** 93곳은 그대로다.
- **값의 표식(`_typeName`)도 안 건드린다.** 그것을 네임스페이스화하는 것은 별개다.
- `Setoid.Struct` 는 레코드라 이번 문법에 안 들어온다(결정 ③).

## 참고 — 남의 것을 실제로 열어 본 결과

| | 표현 | 크기 |
| --- | --- | --- |
| `sanctuary-def` | `{ name, type:'UNARY', arity, types:{$1:…}, extractors:{$1:…} }` | 3,032줄 (검사기 포함) |
| `zod` | `{ type:'array', element:… }` | — |
| **이 계획** | `{ name, args:[…] }` | 파서 13줄 |

**`extractors` 는 배울 만하다** — 타입마다 "안쪽 값을 꺼내는 법" 을 함께 들고 다니면
원소 검사가 그 위에 선다. `Task`·`Reader` 처럼 못 여는 것은 추출기를 안 주면 된다.
**이번 계획에는 넣지 않는다**(원소 검사가 이 계획의 목표가 아니므로). 다만 82개 팩토리를
만들 때 이 자리가 필요해질 것이므로 `args` 옆에 넣을 여지를 남긴다.
