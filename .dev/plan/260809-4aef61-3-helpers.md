# 회차 3 — 미정의 헬퍼 수리

## Context

회차 2에서 API 불일치를 고쳐 55 → 52. 남은 52건의 대부분은 "미정의 헬퍼" 다.
회고에서 이것이 실제로 두 종류임을 확인했다:

- **(a)** 같은 문서 다른 블록에 정의가 있다 → 자동 보충 가능
- **(b)** 문서 어디에도 없다 → 최소 스텁을 손으로 쓰거나 `no-run`

회차 2의 자동 보충 스크립트는 (a) 중 **한 줄짜리 선언만** 처리했다. 여러 줄에 걸친
정의(`const fetchUser = id => Task.fromPromise(\n ... \n);`)는 잘려서 실패했다.

## 변경 사항

### 1. 자동 보충 스크립트 개선 — 여러 줄 정의 지원

선언 시작 줄부터 **괄호 균형이 맞을 때까지** 이어붙여 한 덩어리로 다룬다.
보충 후 그 블록이 실제로 통과하는지 확인하고, 통과하지 않으면 되돌린다
(회차 1에서 반쪽짜리 보충이 새 실패를 만든 적이 있다).

### 2. (b) 스텁 작성 — 최소로

`fetchUser`, `config` 같은 도메인 헬퍼는 예제의 주제가 아니다. 한두 줄로 만든다:

```js
const fetchUser = id => Task.of({ id, name: 'Alice' });
```

**스텁이 세 줄을 넘으면 그 블록은 `no-run` 이 맞다** — 스텁이 예제보다 길어지면
읽는 사람에게 방해다. 그때는 `no-run 외부 헬퍼를 가정한 설명용 예시` 로 표시한다.

### 3. 남은 API 불일치

`Free.liftF: expected a functor`(2), `sequence` 인자 순서, `Functor.map` 인자,
`fs` 접근 블록. 개별 조사한다.

### 4. 마무리 — PENDING 삭제

`PENDING` 이 비면 **상수와 관련 분기 코드를 검사기에서 지운다.** 남겨두면 다음 사람이
새 문서를 거기 넣는다. `CLAUDE.md` 의 PENDING 설명도 함께 지운다(context 클래스이므로
Context 단계에서 처리하거나 `allow` 를 받는다).
