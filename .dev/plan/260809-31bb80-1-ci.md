# GitHub Actions CI 도입

## Context

직전 작업에서 `npm test` 라는 단일 검증 진입점을 만들었다(전체 테스트 + `tsc --noEmit`,
실패 시 non-zero). 하지만 **그 게이트는 로컬에서 누군가 실행할 때만 돈다.**

바로 그 방치가 직전 작업의 원인이었다 — `tests/unit-validation.test.js` 288줄이 몇 달간
실행조차 되지 않은 채 남아 있었고, 아무도 몰랐다. 게이트를 고쳐도 **자동으로 돌지 않으면
같은 일이 재발한다.** CI 는 그 재발을 막는 구조다.

목표: `main` 으로의 push 와 모든 PR 에서 Node 20/22 로 검증이 자동 실행된다.

## 확정된 설계 결정 (사용자 합의)

- **Node 20 + 22 매트릭스.** `engines` 는 `>=20` 으로 맞춘다.
- **빌드는 실행 여부만 확인한다.** `node build.js && node build-types.js` 가 에러 없이
  끝나는지만 보고 산출물은 버린다.
- **`dist/` 를 커밋하거나 업로드하지 않는다.** 그리고 **재빌드 결과를 커밋된 `dist` 와
  비교하지도 않는다** — 빌드 헤더의 `Built:` 타임스탬프는 "사람이 이 빌드를 배포하기로
  결정한 시점" 을 기록하는 **의도된 설계**이므로 항상 diff 가 난다. 나중에 누군가
  `git diff --exit-code dist` 를 CI 에 추가하지 않도록 워크플로에 주석으로 남긴다.

## 이미 확인한 사실 (재조사 불필요)

- `build.js` / `build-types.js` 는 **Node 내장 모듈만** 쓴다 (`fs`, `path`, `url`).
  `npm ci` 가 설치하는 것은 typescript 하나뿐이고 빌드에 외부 의존성이 없다.
- `package-lock.json` 은 `lockfileVersion: 3`, 루트 `packages[""]` 항목에 **`engines` 가
  없다.** → `package.json` 에 `engines` 를 추가하면 락파일과 어긋날 수 있다.
  **`npm install --package-lock-only` 로 락을 갱신해야 한다.**
- 로컬에 `act` 는 없지만 **docker 가 돌고 있다** → `node:20` / `node:22` 컨테이너에서 스텝을
  직접 재현하는 편이 `act` 보다 정확하다.
- **pyyaml 은 YAML 1.1 이라 `on:` 을 불리언 `True` 로 파싱한다.** 구조 검증 스크립트는
  `'on'` 문자열이 아니라 `True` 키를 찾아야 한다. 아니면 "트리거 없음" 으로 오판한다.
- `.github/workflows/` 는 Scaffolding 단계에서 이미 생성했다.
- `CLAUDE.md` 의 CI 섹션은 Context 단계에서 이미 작성했다 (`CLAUDE.md` 는 context 클래스라
  Execution 에서 쓸 수 없다 — 직전 회고의 교훈을 적용했다).

## 변경 사항

### 1. `.github/workflows/ci.yml` (신규)

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read        # 최소 권한 — 이 워크플로는 읽기만 한다

jobs:
  verify:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false  # 한쪽이 깨져도 나머지 버전 결과를 본다
      matrix:
        node: [20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test          # tests/*.test.js 전체 + tsc --noEmit
      # 빌드는 "에러 없이 끝나는가" 만 본다. 산출물은 버린다.
      # dist/ 를 커밋된 것과 비교하지 마라 — 빌드 헤더의 타임스탬프는 의도된 설계라
      # 항상 diff 가 난다. `git diff --exit-code dist` 를 추가하면 CI 가 영구히 깨진다.
      - run: node build.js && node build-types.js
```

`fail-fast: false` 인 이유: Node 20 에서만 깨지는 문제와 양쪽 다 깨지는 문제를 구분하려면
두 잡의 결과가 모두 필요하다. 기본값(`true`)이면 한쪽이 깨질 때 나머지가 취소된다.

`concurrency` 블록은 **넣지 않는다** — YAGNI (`CLAUDE.md` 설계 원칙 5). PR 러시로 CI 시간이
문제가 되면 그때 넣는다.

### 2. `package.json` — `engines`

```json
"engines": { "node": ">=20" }
```

`private: true` 라 배포를 막지는 않지만 지원 런타임을 문서화한다. Node 15 미만에서는
unhandled rejection 이 프로세스를 죽이지 않아 `npm test` 게이트에 구멍이 생긴다
(직전 작업의 codex 검토에서 나온 지적).

### 3. `package-lock.json` — 락 갱신

`npm install --package-lock-only` 로 루트 항목에 `engines` 를 반영한다.
**갱신하지 않으면 CI 의 `npm ci` 가 sync 오류로 깨질 수 있다.** 이건 추측이 아니라
아래 검증 2번에서 실제로 확인한다.

### 4. `CLAUDE.md` — (Context 단계에서 완료)

`### CI` 섹션이 이미 들어가 있다. Verification 에서 실제 워크플로와 내용이 일치하는지
대조한다. 어긋나면 `harness allow` 로 정정한다.

## Verification

Selection 에서 기록한 완료 조건 7개와 대조한다.

**1. YAML 문법 + 구조 검증 (조건 5)**

```bash
python3 - <<'PY'
import yaml
d = yaml.safe_load(open('.github/workflows/ci.yml'))
trig = d.get(True, d.get('on'))        # pyyaml 은 `on:` 을 True 로 읽는다
assert 'push' in trig and 'pull_request' in trig, trig
job = d['jobs']['verify']
assert job['strategy']['matrix']['node'] == [20, 22]
runs = [s['run'] for s in job['steps'] if 'run' in s]
assert runs == ['npm ci', 'npm test', 'node build.js && node build-types.js'], runs
print('OK', trig, runs)
PY
```

**2. Node 20 / 22 에서 스텝을 실제로 실행 (조건 6)** — `act` 없이 docker 로.

**작업 트리를 마운트하지 않는다.** 컨테이너에서 `npm ci` 를 돌리면 로컬 `node_modules` 를
덮어쓴다. `.git` / `node_modules` / `dist` 를 제외한 사본을 스크래치패드에 만들어 거기서
돌린다:

```bash
for v in 20 22; do
  docker run --rm -v "$COPY:/w" -w /w "node:$v" \
    sh -c 'npm ci && npm test && node build.js && node build-types.js'
  echo "node $v => $?"
done
```

양쪽 모두 exit 0 이어야 한다. **`npm ci` 가 락 sync 오류로 깨지면 변경 3번이 필요했다는
뜻이다** — 그 자리에서 락을 갱신하고 재실행한다.

**3. 나머지 조건**

- 조건 1·2: 위 1번 스크립트의 assert 가 곧 검증이다
- 조건 3: 워크플로에 `upload-artifact` / `git commit` / `git diff` 가 없음을 grep 으로 확인
- 조건 4: `node -p "require('./package.json').engines"` → `{ node: '>=20' }`
- 조건 7: `CLAUDE.md` 의 CI 섹션이 실제 워크플로와 일치하는지 대조

**4. 로컬 회귀** — `npm test` 가 여전히 통과하는지 확인(`engines` 추가와 락 갱신이 로컬을
깨지 않았는지).

## 범위 밖

- `concurrency` 블록 (필요해지면 그때)
- 배포/릴리스 워크플로 — 배포는 사람의 결정이라는 프로젝트 방침을 따른다
- 커버리지 리포팅, 배지
- `docs/` 문서 7종, `README.md:7` TypeScript 체크박스 (후보 C·D 로 남아 있음)
