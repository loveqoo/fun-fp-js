# 세션 산출물 커밋 및 main 머지

## Context

세 작업(테스트 게이트 / CI / docs 7종)의 산출물이 전부 미커밋 상태다. 사용자가 커밋과
머지를 요청했고, 세 가지를 결정했다 — `.dev/` **포함**, **작업별 3커밋 + 하네스 1커밋**,
**로컬 머지 후 push**.

머지하면 `feat/ts-support` 의 기존 4커밋(TypeScript 선언)도 함께 `main` 으로 간다.
`main` 은 뒤처져 있고 분기 커밋이 없어 fast-forward 가능하다.

**`origin/main` push 는 이번 세션에서 처음으로 CI 를 실제 실행시킨다.** 지금까지의
CI 검증은 전부 로컬 docker 재현이었다.

## 제약 (조사로 확인)

- **`CLAUDE.md` 가 `@.claude/harness/POLICY.md` 와 `@LEARNED.md` 를 import 한다.**
  두 파일이 빠지면 다른 사람 체크아웃에서 CLAUDE.md 가 깨진다 → 반드시 커밋한다.
- **하네스 가드가 `.claude/harness` 를 인자로 언급하는 모든 Bash 명령을 차단한다.**
  읽기 전용 dry-run 도 막힌다. → `git add .claude/harness/` 를 쓸 수 없다.
  **`git add -A` (경로 미지정)는 허용되고**, `.gitignore` 가 `bin/` 과 `harness.db*` 를
  이미 제외하므로 `LEARNED.md`, `POLICY.md`, `rationale.md`, `stages.json` 만 담긴다
  (dry-run 으로 확인).
- **`dist/` 와 `index.js` 는 이번 세션에 바뀌지 않았다.** 재빌드하지 않는다 —
  빌드 타임스탬프는 사람이 배포를 결정한 시점을 기록하는 의도된 설계다.
- 대화형 `git add -p` / `-i` 는 이 환경에서 쓸 수 없다.

## 커밋 분할

공유 파일(`package.json`, `CLAUDE.md`)이 여러 작업에 걸쳐 수정돼 있어 그대로는 나뉘지
않는다. 처리 방침:

- **`package.json`** — `test` 스크립트(작업 1)와 `engines`(작업 2)가 섞여 있다.
  **한 번의 임시 편집으로 나눈다**: 커밋 1 전에 `engines` 를 뺀 판본을 만들어 커밋하고,
  원본을 복원해 커밋 2에 넣는다. `engines` 는 CI 의 산출물이므로 나눌 값어치가 있다.
- **`CLAUDE.md`** — 세 작업의 문서 갱신이 모두 들어 있다. **나누지 않고 커밋 4에 넣는다.**
  세 번의 파일 수술을 반복할 값어치가 없고, CLAUDE.md 는 프로젝트 가이드라 세션 단위로
  한 번 갱신되는 편이 이력상 자연스럽다. 커밋 메시지에 무엇이 들어갔는지 적는다.

| # | 제목 | 파일 |
| --- | --- | --- |
| 1 | `test: npm test 게이트 도입` | `tests/run.js`, `tests/unit-validation.test.js`, `tests/utils.js`, `package.json`(test 스크립트만) |
| 2 | `ci: GitHub Actions 도입` | `.github/workflows/ci.yml`, `package.json`(engines), `package-lock.json` |
| 3 | `docs: 신규 기능 7종 문서 + 예제 실행 검사기` | `docs/*.md` 7개, `docs/README.md`, `tests/docs-examples.test.js` |
| 4 | `chore: 하네스·설정·작업 기록` | `.claude/harness/*`, `.claude/settings.json`, `.gitignore`, `CLAUDE.md`, `.dev/*` |

커밋 4는 `git add -A` 로 남은 전부를 담는다(앞의 셋이 이미 커밋된 뒤이므로 잔여물만 남는다).

모든 커밋 메시지 끝에 `Claude-Session:` 줄을 붙인다.

## 실행 절차

1. `npm test` — 커밋 전 상태 확인
2. `package.json` 원본을 스크래치패드에 백업 → `engines` 뺀 판본 작성 → 커밋 1
3. 원본 복원 → 커밋 2
4. 커밋 3
5. `git add -A` → 커밋 4
6. `git status` 가 깨끗한지 확인, `npm test` 재실행
7. `git checkout main && git merge feat/ts-support`
8. 머지 직후 `npm test`
9. `git push origin main`
10. GitHub CI 실행 확인 (`gh run list` / `gh run watch`)

## Verification

완료 조건 7개와 1:1 대조한다.

1. **조건 1·2** — `git log --oneline -4` 와 각 커밋의 `git show --stat` 으로 파일 구성 확인
2. **조건 3** — `git status --porcelain` 이 빈 출력
3. **조건 4** — 커밋 직전(절차 1)과 머지 직후(절차 8) 양쪽 `npm test` exit 0
4. **조건 5** — `git log --oneline -1 main` 이 머지 결과를 가리키고
   `git rev-list --count main..feat/ts-support` 가 0
5. **조건 6** — `git rev-list --count origin/main..main` 이 0
6. **조건 7** — **`gh run list` 로 워크플로 실행을 확인하고, Node 20/22 두 잡이 모두
   success 인지 본다.** 로컬 재현이 아니라 GitHub 에서의 첫 실제 실행이다.
   실패하면 그 자리에서 원인을 보고 고친다

## 되돌리는 법 (문제 시)

- push 전이면 `git checkout feat/ts-support && git branch -f main <이전 main SHA>`
- 커밋만 되돌리려면 각 커밋이 독립적이므로 `git revert <sha>` 로 하나씩 가능
- 이전 `main` SHA 는 절차 7 직전에 기록해 둔다
