# 회차 4 회고 — 소유자가 읽지 못하는 코드는 옳아도 지워진다

작업 `260811-15c84c` 회차 4. `Plus` → `Monoid` 유도를 규칙으로 올리고, `view` 의
"정확히 1대상" 을 코드가 강제하게 했다. 리뷰 **위반 12건**.

## 이 회차에서 가장 중요한 것은 코드가 아니다

소유자가 두 번에 걸쳐 말했다:

> "변수 네이밍이 이상하군요. 제가 기존에 그렇게 코딩하지 않았는데 말이죠.
> `_runOptic`, `_PForget` 이런 것도 처음 보네요. **제가 이해하지 못하면 지워지는 거에요.**"
>
> "함수합성이 가능한데 합성하지 않고 직접 구현하는 것은 지울 겁니다.
> 합성에 필요한 타입이 있다면, 기존 타입 등록 및 구현 방법을 보고 구현하면 됩니다."

**나는 optics 섹션에 파일 전체와 다른 규칙을 들여놓고 알리지 않았다.** 언더스코어 접두사 +
약자 10개(`_PFn`, `_PForget`, `_PTagged`, `_runOptic`, `_firstM`, `_arrayM`, `_Identity`,
`_Const`, `_asApplicative`, `_promap`). 그리고 `wander` 같은 Haskell 이름을 설명 없이 썼다.

**그리고 이번 회차가 그걸 악화시켰다** — `_firstMonoid` → `_firstM` 으로 더 줄였고,
`_firstM` 의 `first` 는 같은 파일의 `Semigroup.of('first')` 와 아무 관계가 없다(내용물은
`plus(maybe)`). **이름이 틀린 방향으로 유도한다.**

## 무엇이 통했나

### 사용자 지시가 리뷰어의 발견과 정확히 겹쳤다

리뷰어가 **합성 가능한데 손으로 만든 것 4건**을 실행으로 확인해 왔다:

| 지금 | 조합 | 확인 |
| --- | --- | --- |
| `_asApplicative` (심볼 3개를 손으로 찍음) | `new Applicative(new Apply(new Functor(...)))` | 실행 성공 |
| `_PFn.first` | `Bifunctor.of('tuple').bimap(p, identity, t)` | **완전 일치** |
| `_PFn.left` | `Bifunctor.of('either').bimap(p, identity, e)` | 값 일치 |
| `_PForget.left` | `Either.fold(p, () => monoid.empty(), e)` | 정의상 동일 |

특히 **`_asApplicative` 는 `checkAndSet` 검증을 통째로 건너뛰고 심볼만 위조**해
`Traversable.traverse` 를 통과시키고 있었다. **등록하지 않고 인스턴스를 만드는 정식 경로가
이미 있다** — 생성자에 `registry` 를 안 넘기면 된다. 몰라서가 아니라 안 찾아봐서 우회했다.

### 유도를 규칙으로 올린 것은 작동한다

사용자가 자기 `Plus` 를 등록하면 짝이 따라온다 —
`new Plus(alt, zero, 'Array', Plus.types, 'firstNonEmptyArray')` → `Monoid.of('plus(firstnonemptyarray)')`.
회차 3의 손복사 2개가 사라졌고 `register()` 우회로 생성자 이름 키 오염도 없다(뮤테이션 검거).

### 뮤테이션을 절차로 넣은 것이 즉시 값을 냈다

`view` 가드를 지우니 3건 빨간불, `deriveFromPlus` 호출을 지우니 1건. **그리고 동시에,
내가 약화시킨 테스트도 뮤테이션이 잡았다**(아래).

## 무엇을 잘못 가정했나

### 1. 복잡한 코드를 지우면서 **테스트도 같이 약화시켰다**

사용자가 `semigroup.concat = monoid.concat = plus.alt` 를 "설명이 세 줄 필요한 코드" 라
지적했고 지웠다 — **그 판단은 옳다.** 틀린 것은 테스트를 동일성 비교에서 **값 비교**로
바꾼 것이다:

```javascript
test("Plus 유도 - alt 와 같은 결과를 준다")   // 재래핑을 해도 안 해도 통과한다
```

뮤테이션 확인: 재래핑 제거를 다시 넣어도 38/38 통과. **구별력 0.** 회차 3 #8 의 재발이다.

**코드를 단순하게 만드는 것과 검증을 느슨하게 하는 것은 다른 일인데 한 번에 했다.**

그리고 비용이 무시할 크기가 아니었다 — preview 20000회×100원소에서
HEAD `15.7ms` → 현재 `75.6ms` → 재래핑 제거 시 `46.3ms` (**−39%**). 다시 판단해야 한다.

### 2. 같은 회차에 문서를 코드와 **정면 충돌**시켰다

`CLAUDE.md` 에 이번에 추가한 문단이 `view` 다중 대상을 "**동작을 보증하지 않습니다**" 라
썼다. 그런데 같은 회차에 코드는 결정적으로 던지게 만들었다.

**다음 사람은 "그럼 첫 값이 나오나 보다" 로 읽는다 — 회차 1·2 회귀가 정확히 그 독법에서
나왔다.** Compounding 에서 고쳤다.

### 3. 문서에 **검증 가능하게 거짓인** 문장을 썼다

`docs/Optics.md:196` — "`view`는 항상 값을 돌려주거나 던집니다 — `undefined`를 흘리지 않습니다."

실측: `view(Lens(o=>o.a, ...), { a: undefined })` → **`undefined`**.
`view` 가 세는 것은 **대상 수**이지 값이 아니다. `docs/*.md` 는 예제만 실행되고 산문은
검사되지 않아 통과했다.

### 4. `plus(maybe)` 라는 이름이 주석 30줄을 요구한다

이 구분을 설명하려고 `CLAUDE.md` 12줄 + `index.js` 17줄이 필요했다. `plus(<타입>)` 은
**유래한 타입 클래스**를, `maybe(<inner>)` 는 **감싼 구조**를 넣는다 — 규칙이 다른데
형태가 같아 짝처럼 보인다. **`Plus` 를 모르는 사람에게 `plus(maybe)` 는 정보를 안 준다.**

## 이 회차를 싸게 만들었을 것

### ① 이름 규칙이 다르다는 것을 optics 를 만들 때 알렸어야 했다

3회차 뒤에 소유자가 발견했다. **다른 규칙을 들여놓는 것 자체가 결정이고, 결정은 알려야 한다.**

### ② 손으로 쓰기 전에 레지스트리를 조합으로 검색했어야 했다

판단 규칙 1·2 는 "**인스턴스**가 있나" 를 물었다. 이번에 부족했던 것은 한 단계 더다 —
**"이 동작을 기존 것의 조합으로 얻을 수 있나".** `Bifunctor.of('tuple').bimap` 이
`_PFn.first` 와 완전히 같은데 3회차 동안 아무도 안 봤다.

### ③ 계획 항목을 지울 때 그 항목의 테스트도 함께 재설계했어야 했다

지운 것은 구현이고 남겨야 할 것은 **의도**였다. "재래핑하지 않는다" 를 안 하기로 했으면
테스트를 약화시킬 게 아니라 **지우거나 반대 방향으로 고정**해야 했다.
