## 1. 무엇이 통했나

**로컬 docker 재현이 실제 러너를 정확히 대변했다.** 이번 작업의 진짜 질문은 "CI 가
통과하는가" 가 아니라 **"이틀에 걸친 로컬 검증이 믿을 만했는가"** 였다. 결과:

| | 로컬 docker | GitHub 러너 |
| --- | --- | --- |
| 테스트 파일 | 38 passed, 0 failed | 38 passed, 0 failed |
| 문서 예제 | 108 실행, 7 스킵 | 108 실행, 7 스킵 |
| typecheck / 빌드 | passed / 성공 | passed / 성공 |

숫자가 하나도 어긋나지 않았다. `act` 가 없어서 `node:20`/`node:22` 컨테이너로 스텝을 직접
돌린 판단(작업 260809-31bb80)이 옳았음이 사후 확인됐다. **이 프로젝트 범위에서는 컨테이너
재현으로 CI 를 사전 검증할 수 있다.**

**로그를 눈으로 훑지 않고 grep 했다.** `gh run view --log` 는 3,212줄이다. 계획에 "로그의
숫자를 눈으로 훑지 말고 grep 한다" 를 적어둔 덕에 `test files : 38 passed` 같은 문자열을
직접 뽑아 대조했다. 초록 체크만 보고 넘어갔다면 "38개가 다 돌았는지" 는 확인하지 못했다.

**세 작업이 여기서 맞물렸다.** 테스트 게이트가 CI 에서 돌고, 그 안에서 문서 예제 108개가
실행된다. 이제 문서가 코드와 어긋나면 GitHub 이 빨간불을 켠다 — 세션 첫 작업의 발견
("실행되지 않는 것은 썩는다")에 대한 구조적 답이 완성됐다.

## 2. 무엇을 잘못 가정했나

**액션 버전을 관성으로 골랐다.** 워크플로를 쓸 때 `actions/checkout@v4`,
`actions/setup-node@v4` 를 별 생각 없이 적었다. `@v4` 는 오랫동안 관례였으니까.
그런데 CI 가 **성공하면서 deprecation 주석**을 뱉었다 — v4 는 Node 20 런타임을 쓰는데
그것이 deprecated 라 러너가 강제로 Node 24 에서 돌리고 있다. 현재 최신은 **둘 다 v7** 이다.

즉 **어제 새로 쓴 파일이 이미 낡아 있었다.** 확인 비용은 1초였다:
`gh api repos/actions/checkout/releases/latest --jq .tag_name`

이건 "CI 가 통과했으니 됐다" 로 넘어갔으면 못 봤을 것이다. **성공한 실행의 주석도 읽어야
한다.**

**`verification_evidence` 를 명령 실행만으로 채울 수 있다고 가정했다.** `npm test` 를 다시
돌려도 종료 조건이 채워지지 않았다. 검증 **기록을 파일로** 남겨야 했다
(`.dev/log/260809-bd5e96-1-ci-verification.md`). 하네스는 "검증했다" 가 아니라 "검증한
내용이 남았다" 를 요구한다 — 다음 사람이 무엇을 어떻게 대조했는지 볼 수 있어야 한다.

`.dev/retrospect/INDEX.md` 에 줄을 추가하지 않아 Scaffolding 에서 "INDEX.md 가 최신
