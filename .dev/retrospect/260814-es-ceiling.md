# 260814 — ES2018 상한과 dist 동기화

`static-land-cleanup` 을 `main` 에 병합한 뒤, 소유자가 `index.js` 의 `?.` 를 보고 시작된
회차. 커밋 8개(`main` 직접), `611196f → 536609e`.

| | |
| --- | --- |
| 한 일 | `?.`·`??` 제거 → ES2018 상한 게이트 → 폴리필 축소 → dist 동기화 게이트 → 상한을 저장소 전체로 |
| 심은 결함 | 14종, 14종 다 잡힘 |
| 게이트 | 3개 → **5개** (`es-ceiling`, `dist-sync` 신설) |
| 테스트 파일 | 42 → 44 |

---

## 통한 것

### 「확인 안 함」이 결론을 바꿨다

Apps Script 가 `?.` 를 지원하는지 조사했다. 2차 자료는 전부 "ES2020이니 된다" 고 했고
정황도 그쪽이었다 — 구글 문서가 `#private`(ES2022)를 파싱 에러라고 **콕 집어** 적으면서
`?.` 는 예외 목록에 없다. 평소라면 "지원합니다" 라고 썼을 것이다.

1차 출처를 못 찾았고 실행해 볼 수단도 없어서 **「확인 안 함」** 이라고 적었다. 그리고
그 판단이 결론까지 끌고 갔다 — "확인되지 않은 것에 기대지 않는다" 가 상한을 ES2018로
정하는 근거가 됐다. **규칙이 문장의 톤이 아니라 설계 결정을 바꾼 사례다.**

### 뮤테이션이 내 버그를 세 번 잡았다

셋 다 **테스트가 초록인 상태**에서 잡혔다.

| 버그 | 증상 | 안 잡았으면 |
| --- | --- | --- |
| 규칙표를 평범한 객체로 만듦 | `PROTO_APIS['constructor']` 가 `Object.prototype` 을 타고 참 | 멀쩡한 5곳을 위반이라고 신고 |
| 폴리필 면제를 **블록 전체**로 잡음 | 블록 안에서 검사 없이 직접 부르는 결함이 통과 | 게이트가 보는 척만 함 |
| 빌드 시각 정규화가 비대칭 | 기대값에 `'X'` 를 넘겼는데 치환 대상이 아님 | 거짓 실패 |

두 번째가 특히 그렇다. 결함을 심었는데 **초록이 나왔고**, 파일을 눈으로 보고 결함이 실제로
심어진 것을 확인한 뒤에야 "게이트가 뚫렸다" 고 판정할 수 있었다. 심었다고 믿고 넘어갔으면
"3종 전부 잡음" 이라고 보고했을 것이다.

## 잘못 가정한 것

### ① 틀을 의심하지 않았다 — 가장 비쌌다

`dist/` 를 두고 "내용도 따로 훑을까요" 를 **두 번** 여쭀다. 선택지까지 만들어 드렸다.

소유자: *"dist 는 index.js 와 동일하다고 보는 게 맞습니다. 1개의 진실 소스에서 만들기
때문이죠."*

진실 소스가 하나면 산출물을 다시 훑는 것은 **같은 일을 두 번 하는 것**이다. 물어야 했던
것은 "산출물이 그 소스에서 나온 게 맞는가" 였다. 관점을 바꾸자 게이트가 제 모양을 찾았고
`es-ceiling` 이 `dist/` 를 안 봐도 되는 이유까지 따라 나왔다.

나는 주어진 틀 **안에서** 최적화하고 있었다. 선택지를 만들어 드린 것이 오히려 틀을 굳혔다 —
"A냐 B냐" 를 물으면 "둘 다 아니다" 가 답지에서 사라진다.

### ② 규칙이 있는데도 어겼다

`CLAUDE.md`: *"소유자는 코드를 읽지 않는다 — 매번 쉬운 말로 설명하라."*

「게이트」를 설명 없이 열 번 넘게 썼고, 소유자가 *"게이트가 무슨 뜻인가요? 점검?"* 이라고
물어야 했다. 저장소의 기존 용어라는 것은 이유가 되지 않는다 — 그 용어도 앞선 회차의
에이전트가 만든 것이다. **규칙을 아는 것과 지키는 것은 다르고, 이건 변명이 없다.**

### ③ 검사 도구 없이 숫자를 냈다

개발 파일의 상한 위반이 **23건**이라고 보고했다. 임시 스캐너로 센 값이었다. 실제 게이트를
돌리니 **26건**이었다 — 최상위 `await` 1, 동적 `import()` 2 를 내 스캐너가 안 보고 있었다.

그 전에는 문자열 검색으로 `build-types.js` 에 1건이 있다고 했는데 파서로 세니 **0건**,
오탐이었다. **같은 회차에서 같은 실수를 두 번 했다** — 도구를 만들기 전에 도구의 결론을
말했다.

### ④ 소유자가 깎은 파일을 내가 다시 부풀렸다

이 회차의 진짜 교훈이다. 소유자는 하네스 1,005줄을 걷어내고 `CLAUDE.md` 를 **465줄 →
34줄** 로 깎았다. 나는 오늘 그 파일에 **25줄을 더했다**(34 → 87, 2.5배).

매번 "이건 항상 보여야 하는 규칙" 이라고 판단했다. **하네스가 커진 과정도 매 단계로 보면
그렇게 타당했을 것이다.** 더 나쁜 것은, 이 저장소가 이미 답을 갖고 있다는 점이다 —
"주석은 한 줄로, 길면 `docs/` 에 쓰고 한 줄 힌트만 남겨라." 그 규칙을 `CLAUDE.md` 자신에게
적용하지 않았다. 근거는 이미 `docs/internals.md#es-ceiling` 에 전부 있었다.

## 이 회차를 싸게 만들었을 것

1. **`dist/` 를 처음 물을 때 "진실 소스가 몇 개인가" 를 먼저 셌으면** 두 번의 왕복이 없었다.
   하나면 검사할 것은 내용이 아니라 동기화다 — 셀 수 있는 질문이었다.
2. **스캐너를 임시로 만들지 말고 게이트를 먼저 만들었으면** 23/26 과 1/0 두 번의 정정이
   없었다. 어차피 게이트를 만들 것이었고, 임시 도구는 그 사이의 답만 오염시켰다.
3. **`CLAUDE.md` 에 줄을 더할 때마다 "이게 `docs/` 로 갈 수 있나" 를 물었으면** 25줄이
   3줄이었다.
