## 1. 무엇이 통했나

**분류를 먼저 하고 도구를 그에 맞췄다.** 회차 2 회고에서 "미정의 헬퍼 46건" 을
(a) 같은 문서에 정의가 있는 것 / (b) 없는 것으로 갈라야 한다고 적어뒀다. 실제로 그렇게 하니:

| 단계 | 방법 | 효과 |
| --- | --- | --- |
| (a) | 괄호 균형을 추적해 **여러 줄 정의**를 통째로 보충 | 7건 |
| 법칙·시그니처 | 이유와 함께 `no-run` | 16건 |
| (b) | 타입클래스 구조분해 + 도메인 스텁 | 25건 |

회차 2의 스크립트는 한 줄짜리 선언만 처리해서 `const fetchUser = id => Task.fromPromise(\n...)` 
같은 정의를 잘라 붙였다. 괄호 균형 추적을 넣자 바로 풀렸다.

**자동화가 만든 버그를 두 개 잡았다.**

1. 선언 보충 스크립트가 `Applicative.md` 에 `Functor.of('task')` 를 붙였는데 그 블록은
   `Maybe` 를 쓴다. 문서 안에서 `map` 을 선언하는 줄을 찾다가 **다른 타입의 것**을 집었다.
   회차 2 회고의 "생성 스크립트의 결과도 검증해야 한다" 가 그대로 재현됐다.
2. 줄 번호 기준 삽입이 **코드펜스 바깥**에 들어가 산문 한가운데 `const config = ...` 가
   떠 있었다.

**두 번째가 특히 위험했다 — 검사기는 펜스 안만 보므로 이 손상을 잡지 못한다.**
게이트가 있어도 **그 게이트가 보지 않는 축**이 있다. 그래서 별도 검사를 돌렸다:
펜스 열림/닫힘 균형, 펜스 밖 코드 줄 수. 둘 다 0을 확인했다.
→ **자동 편집 후에는 게이트가 보는 축이 아닌 것도 따로 검사하라.**

## 2. 무엇을 잘못 가정했나

**스텁이 "아무 값이나 되면 된다" 고 가정했다.** `add5 = x => x + 5` 를 넣었더니
`State.composeK(toString, double, add5)` 가 `f(...).run is not a function` 으로 깨졌다.
**`composeK` 는 Kleisli 화살표(`a -> M b`)를 요구**하므로 `x => State.of(x + 5)` 여야 한다.
스텁도 타입이 맞아야 한다 — 이름만 채운다고 되지 않는다.

**줄 번호가 안정적이라고 가정했다.** 같은 파일에 여러 건을 삽입하면서 아래에서 위로
처리했는데도, 검사기가 보고한 줄 번호는 **여는 펜스 줄**이었고 나는 첫 코드 줄로 읽었다.
한 줄 차이로 전부 펜스 밖에 들어갔다.
→ **줄 번호로 편집할 때는 삽입 후 그 자리를 반드시 눈으로 확인한다.**

**남은 15건은 처음부터 손으로 했어야 했다.** 자동화의 수익 곡선이 꺾이는 지점이 있었다 —
52 → 25 까지는 스크립트가 압도적으로 빨랐지만, 그 뒤로는 건별 판단(스텁의 타입, 문서 의도)이
필요해 스크립트가 오히려 버그를 만들었다.
