# 회고 — Free DSL 설계 7회 실패 (2026-08-16)

## 무슨 일이 있었나

소유자가 "Free 를 몰라도 쓰는 DSL" 을 요청했고, 에이전트가 일곱 번 설계를 냈으며 전부
기각됐다: ① liftF+함자클래스(내부 노출) ② command(Cmd)(클래스 어색) ③ op 스마트 생성자
(어색) ④ 제너레이터 do-표기(원한 것 아님) ⑤ 노드+AST(순수함수 조합 아님) ⑥ 봇 전투
effects(단일 객체 편향) ⑦ 다운로더 재작성(거의 도달, 그러나 여전히 부족).

## 실패의 구조 — 마지막 신호에 과최적화

매 회차의 설계가 **직전 피드백 한 축**만 극대화했다. "숨겨라"→은닉 극대화(제너레이터),
"AST"→데이터 노출 극대화(심볼릭까지), "이종 합성"→워크플로 극대화. 축적된 요구 전체
(은닉 + 순수 함수의 조합 + AST 트리 + 이종 기능 + 로직의 자리 + 선언의 의미)를 **동시에**
들고 검사한 회차가 한 번도 없었다. 소유자 표현: "DSL 최적화 로직이 너무 한쪽으로 편향돼서
제대로 정의하지 못한다."

## 가장 비싼 단일 실수

**소유자의 실물 코드(비디오 다운로더)를 처음에 요청하지 않은 것.** 소유자는 처음부터
Free 를 실전에서 쓴 코드를 갖고 있었고, 그것이 7회차에야 나왔다. 실물이 나온 순간 요구의
절반("이종 기능", "pipeK 거시구조", "Command 부기 제거")이 즉시 명확해졌다. 반대로
잘 된 선례: `pipeWhile` 은 **소유자가 설계 스케치를 먼저 냈고** 에이전트는 검증·다듬기만
했다 — 한 번에 통과했다.

## 규칙 (다음 설계 작업에 적용)

1. **설계 요청을 받으면 실물부터 요청하라** — "이상형 코드 몇 줄" 또는 "예전에 쓰던 코드".
   실물 없이 설계를 선제하지 마라.
2. **제약 전체를 명시적 체크리스트로 들고, 매 시안을 전 항목 동시 검사하라.** 직전 피드백은
   체크리스트에 *추가*되는 것이지 새 목표가 아니다.
3. **소유자가 설계자, 에이전트는 구현·검증자**가 이 프로젝트의 잘 되는 협업 모양이다.

## 이 시점까지 축적된 Free DSL 요구 (미래 회차의 입력)

- Free·함자·심볼·liftF 가 사용자 코드에 안 보일 것 (은닉)
- 순수 로직이 이름 있는 함수로 일급일 것 — 검증·판정·변환의 자리
- 노드는 함수 호출로 쉽게 생성, 프로그램은 트리/AST 로 노출 가능할 것
- 단일 객체 로직이 아니라 이종 기능(대화·프로세스·출력…)의 자유 합성일 것
- pipeK 거시 구조와 chain/map 미시 합성이 공존할 것 (소유자 실전 스타일)
- Command 클래스·`.map(command.next)` 부기가 사라질 것
- 효과 선언이 이름 이상의 의미(시그니처)를 담을 수 있을 것 (미해결)
- AST 노출이 일급일 것 (미해결)
- DSL 이 하나의 단위로 묶일 것 (미해결 후보)
