# 회차 5 회고 — 관측 동등한 변경은 게이트가 없다

작업 `260811-15c84c` 회차 5. 소유자 지시 —
**"함수합성이 가능한데 합성하지 않고 직접 구현하는 것은 지울 겁니다."**

회차 4 리뷰 12건 중 **7건 해결**, 새 위반 8건.

## 무엇이 통했나

### 지시가 리뷰어의 실측 목록과 정확히 겹쳤다

소유자가 방향을 말했고, 리뷰어가 **실행으로 확인한 치환 목록**을 냈다. 추측 없이 4건을 고쳤다:

| 지금 | 조합 |
| --- | --- |
| `_asApplicative` (심볼 3개를 손으로 찍어 검증 우회) | `new Applicative(new Apply(new Functor(...)))` |
| `_PFn.first` | `Bifunctor.of('tuple').bimap(p, identity, t)` |
| `_PFn.left` | `Bifunctor.of('either').bimap(p, identity, e)` |
| `_PForget.left` | `Either.fold(p, () => monoid.empty(), e)` |

**검증이 실제로 돌아온 것을 확인했다** — 생성자 경로는 `Functor.map`/`Applicative.of` 에서
잘못된 인자를 즉시 거부하고, 심볼 위조는 **아무것도 검증하지 않았다.**

그리고 53케이스 격자에서 **새 관측 차이 0건.** 순수 리팩터였다.

## 무엇을 잘못 가정했나

### 1. "대안이 없다" 를 확인 없이 주석으로 썼다

```javascript
// 짝의 왼쪽만 꺼내는 fst 는 레지스트리에 없다 — 이것만 손으로 쓴다.
```

**`Comonad.of('array').extract([3,'s'])` → `3`.** `fst` 라는 **이름**이 없을 뿐 연산은
등록돼 있다. 나는 `fp.fst === undefined` 만 보고 "없다" 고 결론냈다.

**이름으로 찾고 없으면 없다고 쓴 것이다.** 규칙 2("이 이름이 있나가 아니라 이 연산이 있나")를
세 회차 전에 내가 썼는데 또 어겼다. 게다가 **두 줄 위에서 튜플을 `Bifunctor.of('tuple')` 로
다루기로 해놓고** head 를 꺼내는 데는 같은 규칙을 안 썼다.

### 2. `composeOptic` 이 함수 합성을 손으로 쓰는 것을 세 회차 동안 못 봤다

```javascript
return P => pab => optics.reduceRight((acc, o) => o(P)(acc), pab);
```

`compose` 가 같은 파일 `index.js:127` 에 있고 export 돼 있다. **바로 위 주석이
"optic 합성 = 함수 합성" 이라 쓰고는 함수 합성을 안 쓴다.**

`set` 의 `() => b`(→ `constant(b)`), `a => Either.Left(a)`(→ `Either.Left`),
`(F,f,s) => instance.traverse(F,f,s)`(→ `instance.traverse`)도 같다.

**나는 "타입 클래스 인스턴스" 만 조합 대상으로 봤다.** `compose`/`constant` 같은 **핵심
유틸리티**도 조합 대상이라는 것을 안 봤다 — 파일의 3~370줄이 통째로 그것들인데.

### 3. 성능을 재지 않았다 — **20배 느려졌다**

계획서 Verification 3항목(baseline / npm test / 뮤테이션)에 **성능이 없었다.**

| | HEAD | 현재 |
| --- | --- | --- |
| `preview` | 10.9ms | **221.3ms (20배)** |
| `toListOf` | 96.5ms | 367.2ms |
| `over` | 111.0ms | 263.0ms |

리뷰어가 하나씩 되돌려 분해했다 — **조합이 원인이 아니다**(`bimap` 되돌려도 그대로,
캐싱은 −4%). 주범은 **클래스 생성자 체인이 원소마다 검증 래퍼를 통과시키는 것**이고,
`Applicative → Apply → Functor` 가 **이중 래핑**한다.

**"검증을 건너뛰지 않는다" 의 대가가 20배다.** 회차 4 리뷰가 재래핑 제거로 회수 가능함을
보였는데 회차 8로 미뤄뒀다 — 그 값이 이번 회차에 훨씬 비싸졌다.

**구조를 바꿀 때 그 대가를 숫자로 남기지 않으면, 다음 사람이 "느려서" 되돌린다.**

### 4. 같은 diff 가 이름을 지우면서 그 이름으로 문서를 썼다

`CLAUDE.md` 6곳이 `_PFn`/`_PForget`/`_PTagged`/`_Identity`/`_Const` 를 아직 부른다.
**그중 301줄은 내가 이번 세션에 새로 쓴 문단이다.** 이 단계에서 7건 치환했다.

## 이 회차를 싸게 만들었을 것

### ① 조합 후보를 "타입 클래스" 로 좁히지 말았어야 했다

리뷰어가 찾은 5건 중 **3건이 핵심 유틸리티**(`compose`, `constant`, `Either.Left`)다.
`index.js` 3~370줄이 전부 그런 것들인데 나는 레지스트리만 뒤졌다.

### ② "없다" 를 쓰기 전에 **연산으로** 한 번 더 봤어야 했다

`fp.fst === undefined` 는 이름 검색이다. `Comonad.types` 를 열어 `extract` 가 무엇을 하는지
봤으면 5초였다. 규칙 2를 내가 썼는데 이름 검색으로 돌아갔다.

### ③ 구조 변경의 계획서에 **성능 측정을 넣었어야 했다**

`npm run baseline` 은 **값**만 본다. 검증 래퍼를 늘리는 변경은 값이 안 바뀌므로 격자로는
영원히 안 잡힌다.

## 이 회차가 드러낸 구조적 한계

**이번 회차의 두 핵심 주장 모두 뮤테이션으로 안 잡힌다:**

| 뮤테이션 | 결과 |
| --- | --- |
| `bimap` 조합 → 손코드 복원 | 38/38 통과 |
| 클래스 Applicative → **심볼 위조 복원** | **38/38 통과** |

둘 다 **관측 동등**이라 테스트로도 격자로도 원리적으로 못 잡는다.

**"합성으로 썼는가" 를 지키는 것은 리뷰어뿐이다.** 이건 결함이 아니라 사실이고, 명시해야
한다 — 초록불을 "규칙을 지켰다" 로 읽으면 안 된다.

유일한 예외: **등록하면 게이트가 생긴다.** `Applicative.of('identity')` 로 꺼낼 수 있으면
`instanceof Applicative`·검사 동작을 테스트로 고정할 수 있다. 그래서 회차 6의 등록은
"구조 교정" 이면서 동시에 **검증 수단**이다.
