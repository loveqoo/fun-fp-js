# 회고 — Optics 문서 재구성 (260811-77313b · 회차 1, 작업 종료)

완료 조건 8개 전부 충족. 사용자 피드백 한 줄("optics 문서가 너무 어렵다")에서 시작했다.

## 1. 무엇이 통했나

**"어렵다" 를 숫자로 바꿨다.** 주관적 피드백이라 그대로는 고칠 수 없었다. **첫 실행 예제까지의
행 번호**를 재니 문제가 즉시 보였다:

| 문서 | 전 | 후 |
| --- | --- | --- |
| `Optics.md` | 68행 | **19행** |
| `Lens.md` | 52행 | **10행** |
| `Maybe.md` (기존) | 16행 | — |
| `Either.md` (기존) | 18행 | — |

기존 30종이 20행 안에 코드를 보여주는데 내가 쓴 둘만 60행 넘게 이론을 읽혔다. **비교 대상이
이미 저장소 안에 있었다** — 내 문서가 이질적이라는 것을 재는 데 grep 한 줄이면 됐다.

→ **주관적 품질 피드백은 저장소 안의 기존 사례와 비교해 수치화하라.**

**진단이 정확하니 처방이 자명했다.** 원인은 분량이 아니라 **배치**였다 — `## 개념` 에 이론
블록 셋(인코딩 공식, Forget/Tagged 표, first/left/wander 표)을 앞세웠다. 전부 구현 세부고,
라이브러리를 *쓰는* 사람은 `P` 를 직접 다루지 않는다.

**이론을 지우지 않고 뒤로 옮긴 것.** 사용자가 "문서 끝 내부 구조 절로 이동" 을 골랐다.
`review` 가 왜 Lens 에서 안 되는지 궁금한 사람이 문서를 떠나지 않아도 된다.
**"어렵다" 의 해법이 "지운다" 는 아니다 — 순서다.**

**예제 수로 무손실을 검증했다.** 재배치는 내용을 흘리기 쉽다. 검사기가 세는 예제 수가
전후 동일한지(Optics 23, Lens 14) 확인했다. **순서만 바꿨다는 주장을 기계가 뒷받침한다.**

## 2. 무엇을 잘못 가정했나

**"정확하면 좋은 문서" 라고 가정했다.** 내가 쓴 이론 블록은 전부 사실이고 검증까지 됐다.
그런데 **독자가 그 시점에 필요로 하지 않는 사실**이었다. 정확성과 가독성은 다른 축이다.

특히 `## 왜 Prism과 Traversal인가?` 라는 제목은 **내가 만든 순서**(Lens 먼저, 나중에 둘 추가)를
그대로 드러낸 것이었다. 독자는 그 역사를 모르고 알 필요도 없다. 독자의 질문은 "왜 여러 종류가
필요한가" 다.
→ **제목이 구현 이력을 반영하고 있으면 독자 관심사로 바꿔라.**

**부제에서 Iso 를 빠뜨렸다.** Iso 를 추가하면서 본문만 고치고 부제("Lens, Prism, Traversal")는
그대로 뒀다. 문서 맨 윗줄인데 못 봤다.

## 3. 이 회차를 싸게 만들었을 것은

**문서를 쓸 때 첫 예제 행 번호를 확인했으면** 이 회차가 없었다. 측정에 5초다.
`grep -n '^```javascript$' docs/X.md | head -1`
→ **새 문서를 쓰면 기존 문서와 같은 지표를 재본다.** 분량·첫 예제 위치·섹션 구성.

**profunctor 전환 때 문서를 "갱신" 만 하고 재검토하지 않았다.** 인코딩이 바뀌면서 이론
블록이 늘었는데, 늘어난 만큼 독자 경로가 나빠진 것을 보지 않았다. **구현이 바뀌어 문서를
고칠 때는 고친 부분만 보지 말고 문서 전체의 읽기 경로를 다시 봐야 한다.**
