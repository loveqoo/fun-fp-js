# 회고 — CI 액션 버전 v4 → v7 (260809-8a8826 · 회차 1)

완료 조건 6개 전부 충족. deprecated 주석 **6건 → 0건**.

## 1. 무엇이 통했나

**직전 실행과 숫자로 대조했다.** "경고가 사라졌다" 를 눈으로 확인하는 대신 두 실행의 로그
전체에서 `is deprecated` 문자열을 세었다 — v4 실행 6건, v7 실행 0건. GitHub annotations
API 도 양쪽 잡 모두 `0` 을 반환했다. **before/after 를 같은 방법으로 재면 "고쳐졌다" 가
주장이 아니라 측정이 된다.**

**메이저를 셋 건너뛰는 대신 릴리스 노트를 실제로 읽었다.** v5·v6·v7 을 각각 조회해
breaking change 를 표로 정리했고, 그중 둘이 진짜 breaking 이었다
(setup-node v5 의 자동 캐싱, v6 의 npm 한정). 우리에게 영향이 없다고 판단한 근거는
**`package.json` 에 `packageManager` 필드가 없다**는 확인된 사실이었지 추측이 아니었다.
실행 결과가 그 판단을 그대로 지지했다.

**중간 메이저에 머무르지 않았다.** 계획을 쓰다가 `@v5` 로 갈지 `@v7` 로 갈지 갈렸는데,
"deprecation 을 없애는 것이 목적이고 조사도 v7 까지 마쳤으니 중간에 서면 같은 일을 또
한다" 로 정리했다. 부채를 절반만 갚는 것은 다음에 같은 작업을 예약하는 것이다.

## 2. 무엇을 잘못 가정했나

**`verification_evidence` 가 검증 기록 파일로 채워진다고 가정했다.** 직전 작업에서 파일을
쓴 직후 종료 조건이 충족되기에 파일이 원인이라고 믿었다. 실제로는
`stages.json` 의 `evidence_signals` 가 **Bash 명령 패턴**을 본다:

```
npm/pnpm/yarn/bun test · pytest · go test · cargo test · make test|check|lint
vitest · jest · ruff · mypy · tsc · --dry-run
```

또는 `Agent`/`Task` 도구, 브라우저 MCP 호출. 직전 작업에서는 파일을 쓰기 **전에** 돌린
`npm test` 가 한 박자 늦게 잡힌 것이었다.

이번 검증은 `gh run view` 와 grep 위주여서 하나도 매치되지 않았다. **하네스가 "검증했다"
로 인정하는 것과 내가 검증이라고 생각한 것이 달랐다.** 원인을 추측하지 않고
`stages.json` 을 직접 읽어 확인했다 — 그게 정답이었다.

→ **규칙: 하네스가 무언가를 요구하는데 이유를 모르겠으면 `stages.json` 을 읽어라.**
   추측으로 파일을 하나 더 쓰는 것보다 빠르다.

## 3. 이 회차를 싸게 만들었을 것은

**액션 버전은 워크플로를 처음 쓸 때 확인했어야 했다** (직전 회고의 규칙 14로 이미 올렸다).
이번 작업 자체가 그 누락의 비용이다 — 커밋 하나, CI 실행 하나, 회차 하나.
1초짜리 확인(`gh api repos/actions/checkout/releases/latest --jq .tag_name`)을 건너뛴 대가다.

**로컬 사전 재현이 불가능한 종류를 구분했어야 했다.** 직전 작업에서 docker 재현이 실제
러너와 숫자까지 일치해서 "로컬로 다 볼 수 있다" 는 인상이 남았다. 하지만 그것은
`npm ci`/`npm test`/빌드 같은 **스텝 내용**에 대한 것이고, **액션 자체는 러너에서만 돈다.**
액션 버전 변경은 actionlint(스키마)로 거르고 실제 CI 로 확인하는 수밖에 없다.
계획에 이 한계를 적어둔 덕에 헛되이 docker 재현을 시도하지 않았다.
