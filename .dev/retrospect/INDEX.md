## 반복 적용할 규칙 (회고에서 뽑은 것)

아직 `harness promote` 임계(여러 작업 반복)에 닿지 않았지만, 두 회차에서 값이 확인된 것들:

1. **게이트를 만드는 작업의 완료 조건에는 실패 주입이 들어가야 한다.** 통과만 보면 게이트가
   놀고 있어도 모른다. 이건 검증 대상뿐 아니라 **검증 도구 자체**에도 적용된다
   (actionlint 를 일부러 깨서 잡는지 확인한 것처럼).
2. **계획 단계에서 변경 대상 파일의 쓰기 클래스를 먼저 확인한다.** context 클래스
   (`CLAUDE.md`)는 Context 단계에서 써야 한다. 회차 1에서 `allow` 왕복을 했고, 회차 2에서
   미리 확인해 없앴다.
3. **지난 작업의 산출물을 정정할 때는 그 파일을 편집하지 말고 같은 폴더의 `INDEX.md` 에
   정정을 쓴다.** `harness allow` 는 경로 클래스 예외라 **파일명 접두사 규칙
   (`loop_prefix`)에는 통하지 않는다.** 둘은 별개의 게이트다.
4. **디렉터리 사본은 블랙리스트(`--exclude`)가 아니라 화이트리스트로 뜬다.** 하네스는
   `.claude` 를 인자로 언급만 해도 차단한다 — 제외 지시여도 마찬가지다.
5. **검증 도구를 만들 때는 "도구가 놀고 있어도 초록불인 경로" 를 먼저 찾아 막는다.**
   예제 검사기의 최악은 예제가 틀리는 게 아니라 **0개를 실행하고 통과하는 것**이다
   (allowlist 오타 하나면 그렇게 된다). 그런 경로마다 명시적 가드를 넣고, 일부러 그 상황을
   만들어 가드가 발동하는지 확인한다.
6. **문서를 쓸 때 1차 재료는 소스가 아니라 테스트다.** 소스는 무엇이 가능한지 알려주고,
   테스트는 무엇이 실제로 동작하는지 알려준다. 검사기가 있으면 서술이 실행으로 교정된다.
7. **기존 구조에 이름으로 편입되는 쪽이 배선을 추가하는 쪽보다 낫다.**
   `tests/docs-examples.test.js` 는 `*.test.js` 패턴에 걸려 러너가 자동으로 집어갔다 —
   러너도 CI 도 수정 불필요했다.
8. **프로젝트 자체 문서(`CLAUDE.md` 포함)도 검증 대상이다.** 실행되지 않는 예제는 언제든
   코드와 어긋나 있다. 실제로 `CLAUDE.md` 의 Transformer 예제 두 개가 서로 모순이었다
   (객체 `StateT(Maybe)` 로 만들면 `Functor.of('statet(maybe)')` 조회가 실패한다).
9. **문서의 주장을 `try/catch` 예제로 넣으면 문서가 회귀 테스트가 된다.** "이러면 TypeError"
   를 산문으로 쓰지 말고 검사기가 실행하는 블록으로 써라.
10. **같은 이름의 API 라도 타입마다 형태가 다를 수 있다.** `Task.catchError` 는 인스턴스
    메서드지만 `EitherT.catchError` 는 정적이고 인자가 `(program, handler)` 다. 유추 금지.
11. **Bash 도구의 작업 디렉터리는 호출 간 유지된다** — `cd` 접두사를 붙이지 마라.
    뒤따르는 명령이 실패하면 `cd` 실패로 집계된다.
12. **"기계적으로 검증할 수 없다" 는 것 자체는 결함의 근거가 아니다.** 검증 가능성이 목표가
   아닌 영역이 있다 (`dist` 빌드 타임스탬프 — 사람의 배포 결정 시점을 기록하는 의도된 설계).
   설계 의도를 먼저 묻는다.
