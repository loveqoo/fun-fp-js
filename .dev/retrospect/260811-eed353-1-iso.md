검색 키: `Iso` `dimap` `TDZ` `구조분해` `optic 계층`

# 회고 — Optics 에 Iso 추가 (260811-eed353 · 회차 1, 작업 종료)

완료 조건 8개 전부 충족. 구현은 **한 줄**이었다.

```js
const Iso = (to, from) => P => pab => P.dimap(to, from, pab);
```

## 1. 무엇이 통했나

**직전 전환의 배당이었다.** van Laarhoven 이었다면 Iso 도 `review` 때문에 또 심볼 표식을
붙여야 했을 것이다. profunctor 로 옮긴 뒤라 `dimap` 한 줄로 끝났고, **모든 연산이 저절로
동작했다** — 세 P 가 전부 `dimap` 을 가지기 때문이다.

이게 "요구하는 것이 적을수록 쓸 수 있는 곳이 많다" 를 눈으로 보여준다:

| optic | 쓰는 메서드 | 동작하는 P |
| --- | --- | --- |
| `Iso` | `dimap`만 | 셋 다 → view, review 둘 다 됨 |
| `Lens` | `first` | 함수·Forget (Tagged 제외) |
| `Prism` | `left` | 셋 다 → review 됨 |
| `Traversal` | `wander` | 함수·Forget |

**구조가 옳으면 확장이 싸진다** 는 것을 두 회차 연속으로 확인했다.

**뒤집은 Iso 에 전용 함수를 넣지 않았다.** `Iso(a => review(iso, a), s => view(iso, s))` 로
유도되므로 문서에 방법만 적었다. API 표면을 늘리지 않으면서 기능은 준다.

**계획에 "구현 깨뜨리기" 를 미리 적어둔 것.** `to`/`from` 순서를 뒤집는 것이 이 구현에서
가장 그럴듯한 실수인데, 그것을 주입해봤고 잡혔다. 한 줄짜리 구현이라도 **틀릴 수 있는
방식은 정해져 있다.**

## 2. 무엇을 잘못 가정했다

**테스트 파일에서 선언 순서를 신경 쓰지 않았다.** Iso 절을 Prism 절보다 앞에 넣었는데,
`review`/`preview`/`toListOf` 는 Prism 절에서 구조분해하고 있었다 →
`Cannot access 'review' before initialization` (TDZ).

수동 검증(`node -e` 로 직접 실행)에서는 통과했기 때문에 더 헷갈렸다. **파일 안의 위치가
만드는 문제는 조각으로 검증할 때 안 보인다.**

해결은 구조분해를 **파일 상단 한 곳으로 모으는 것**이었다. 절이 늘어날 때마다 구조분해를
그 절에 붙이던 방식이 애초에 취약했다.
→ **규칙: 테스트 파일의 구조분해는 상단 한 곳에 모은다.** 절 단위로 흩으면 절 순서를
   바꿀 때 TDZ 를 밟는다.

## 3. 이 회차를 싸게 만들었을 것은

**직전 작업의 프로토타입에 Iso 가 이미 있었다.** 그때 "범위 밖" 으로 빼두고 이번에 다시
만들었다. 판단 자체는 옳았지만(사용자 요청 범위를 지킴), 프로토타입 코드를 회고에 남겼다면
이번에 바로 가져다 썼을 것이다.
→ **범위 밖으로 빼는 것과 결과를 버리는 것은 다르다.** 프로토타입에서 확인한 것은 회고에
   코드째 남겨라.

## 남은 것

- `Optional` — `composeOptic(lens, prism)` 으로 이미 만들어진다. 전용 생성자는 타입 수준
  구분이 목적일 때만 값어치가 있다
- `Fold` / `Getter` / `Setter` — `toListOf`/`view`/`over` 로 이미 된다. 같은 이유
- **TS 브랜드** — 지금 네 optic 이 TS 에서 같은 shape 라 `review(lens, x)` 가 컴파일 타임에
  안 걸린다(런타임은 걸린다). Profunctor 딕셔너리 타입을 optic 종류별로 나누면 가능하다
- `traversed` 가 쓸 수 있는 Traversable 이 array/maybe/either 셋뿐
