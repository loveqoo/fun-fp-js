소유자 지적에서 시작했다 — *"이미 존재하는(함수 합성으로 구현 가능한) 함수를 자체적으로

## 통한 것

### 게이트가 내 설계를 세 번 바로잡았다

**전부 내 눈으로는 못 볼 것이었다.** 코드는 잘 돌았고 즉석 인스턴스도 멀쩡했다.

| 게이트가 멈춘 자리 | 내가 놓친 것 |
| --- | --- |
| 명세 ① `Strong.FunctionProfunctor: first 없음` | JS **정적 상속** — `withTypeRegistry` 를 안 부르면 `Strong.types` 가 `Profunctor.types` 를 그대로 가리켜 남의 인스턴스를 자기 것으로 착각한다 |
| 명세 ③ `.type='any'` 인 Functor 없음 | `Tagged` 를 `Profunctor` 로 등록하면 명세를 못 지킨다. 등록을 뗐다 |
| 명세 ⑤ 문서 그래프에 `Lens/Prism/Traversal` | 코드 블록 안에 쓴 설명을 타입 클래스 이름으로 읽었다 |

두 번째가 특히 그렇다. **"지킬 수 없는 보증은 걸지 않는다"** 는 `Filterable` 판단을 게이트가
나 대신 적용해 줬다.

### 유틸리티를 먼저 읽으라는 지시가 새 코드를 0으로 만들었다

소유자: *"내부에 존재하는 가벼운 유틸성 함수를 이해하고 진행하십시오. 이 도구는 기능은
단순하지만 어떤 타입클래스보다 강력합니다."*

읽고 나니 **새로 쓸 것이 없었다.**

```
fst  = apply(identity)          snd  = apply(flip(identity))
swap = apply(flip(tuple))       튜플 만들기 = converge(tuple, getter, identity)
Forget.first = compose2(p, fst)
```

`t[0]` 을 손으로 안 썼기 때문에 **`apply` 의 인자 검증을 그대로 물려받았다** —
`fst(42)` 가 `apply: args must be an array` 로 던진다. 새 예외 처리가 필요 없었다.

### 뮤테이션이 내 구멍을 두 번 잡았다

둘 다 **테스트가 초록인 상태**였다.

## 잘못한 것

### ① 계획이 이름 변경을 못 셌다 — 완료조건 하나를 못 지킨 원인

계획서에 "건드려야 하는 자리" 를 실측으로 **아홉 개** 셌다. 규칙표 37개, `.d.ts` 48개,
`SPEC` 24항목, 개수 단언 127… 파일 단위로는 빠짐없이 셌다.

**그런데 사설 딕셔너리를 등록 인스턴스로 바꾸면 메서드 이름도 그쪽을 따라가야 한다는 것을
안 셌다.** optic 이 부르던 `P.dimap` 이 `P.promap` 이 되어야 했고, 그래서 완료조건
④("`tests/optics.test.js` 를 한 줄도 안 고치고 통과")를 못 지켰다.

**파일을 세는 것과 결과를 세는 것은 다르다.** "무엇을 건드리나" 는 셌지만 "그러면 무엇이
따라 바뀌나" 는 안 셌다.

### ② 새 공개 표면을 감시 없이 **두 번** 냈다

| 낸 것 | 심은 결함 | 그때 잡혔나 |
| --- | --- | --- |
| `fst` / `snd` | `fst` 를 `snd` 로 바꿔치기 | **안 잡힘** — 쓰는 곳도 테스트도 없었다 |
| `Forget.right` 등 | `right` 가 값을 통과시키게 | **안 잡힘** — optics 가 `right` 를 안 쓴다 |

두 번째는 첫 번째를 겪은 **직후**였다. 같은 회차에서 같은 실수를 반복했다.

원인은 하나다 — **"쓰이는 곳" 을 기준으로 감시를 생각했다.** 표준으로 낸 것은 쓰이지 않아도
계약이므로 그 자체로 검사가 필요하다. 소유자가 `second`/`right` 를 낼지 물었을 때 내가
"쓰지 않는 코드 2개가 생긴다" 고 답한 것도 같은 잘못이다 — 사용처로 셌지 계약으로 안 셌다.
(실제로는 `Tagged.right` 가 **빠져 있던** 것이라 표준으로 가는 게 결함 수정이었다.)

그리고 그 구멍을 막으려 쓴 테스트도 **한 번 뚫렸다.** `Tagged.right` 를 `Left` 로 바꿔도
통과했는데 `.value` 만 봤기 때문이다 — `Left(7)` 과 `Right(7)` 의 `value` 가 둘 다 `7` 이다.

### ③ 거짓 주석 — 검사기가 안 보는 자리

문서 예제에 `second(x*10, [3,'c'])` 의 결과를 `[3,'c']` 라고 적었다. 실제는 `[3, NaN]`
이다(`'c' * 10`). **문서 예제는 실행되지만 검사기가 기대값(`// …`)을 대조하지 않는다** —
그 한계는 이미 파일에 적혀 있었고 나는 읽고도 걸렸다.

### ④ 용어를 설명 없이 썼다 — **어제 회고에 적은 것이 그대로 재발했다**

어제(`260814-es-ceiling.md`) 실패 ②로 적었다: *"「게이트」를 설명 없이 열 번 넘게 썼고
소유자가 뜻을 물어야 했다."*

**적어 놓고 같은 회차에 네 번 더 반복했다.**

| 소유자가 물어야 했던 것 |
| --- |
| "게이트가 무슨 뜻인가요? 점검?" |
| "제가 Const에 대해 모릅니다" |
| "Const를 불러야 생긴다는 의미가 뭐죠?" |
| "이해가 안 되는 부분. tagged, Wander 법칙이 0인 이유" |

**회고에 적는 것으로는 안 고쳐졌다.** 이 저장소가 이미 경고한 그것이다 — *"목록을 늘리는
것으로 재발을 막았다고 생각하지 마라."*

기계로 막을 수 있는 종류가 아니다. 규칙도 이미 있다(`CLAUDE.md`: "소유자는 코드를 읽지
않는다 — 매번 쉬운 말로 설명하라"). **규칙이 없어서가 아니라 발동 시점을 못 잡아서다.**
그래서 규칙을 하나 더 만들지 않고 **발동 조건**을 적는다 — 아래 규칙 97.

## 이 회차를 싸게 만들었을 것

1. **계획서의 "건드릴 자리" 옆에 "그러면 따라 바뀌는 것" 칸을 뒀으면** ④를 못 지킬 일이
   없었다. 파일 목록은 셌는데 파급은 안 셌다.
2. **공개 이름을 낼 때 테스트를 같은 커밋에 넣었으면** 같은 구멍을 두 번 안 냈다.
   "쓰이는 곳이 없어서 나중에" 가 곧 감시 0이다.
3. **개념 이름을 처음 쓸 때 그 자리에서 한 문장을 붙였으면** 소유자가 네 번 멈추지 않았다.
