# 회고 — Transformer 4종 문서 + README 인덱스 (260809-2eb397 · 회차 2, 작업 종료)

완료 조건 8개 전부 충족. 최종: **7종 문서 2,506줄, 실행 검증된 예제 108개.**

## 1. 무엇이 통했나

**문서를 쓰면서 라이브러리의 실제 결함을 찾았다.** 이번 회차 최대 성과는 문서가 아니라
**발견**이다. `Functor.of('statet(maybe)')` 를 예제로 쓰려다 실패해서 파고들었더니:

| 호출 | `_typeName` | 레지스트리 alias |
| --- | --- | --- |
| `StateT('maybe')` | `StateT(Maybe)` | `statet(maybe)` |
| `StateT(Maybe)` | `StateT(M1)` | `statet(m1)` — 실행 순서 의존 |

두 형태는 **다른 클래스**이고 nominal typing 이 강제되므로 섞으면 `TypeError` 다.
`index.js:2351-2353` 에 주석으로만 있고 사용자 문서엔 없었다. 게다가 **`CLAUDE.md` 의 두
예제가 서로 모순**이었다 — 사용 예는 객체 형태(`StateT(Maybe)`)인데 타입클래스 예는
`Functor.of('statet(maybe)')` 라 문자열 형태를 전제한다. 객체로 만들면 그 조회는 실패한다.

**예제를 실행해야만 하는 규칙이 이걸 강제로 드러냈다.** 검사기가 없었다면 CLAUDE.md 를
그대로 베껴 4종 문서에 오류를 복제했을 것이다. 이것이 회차 1의 "문서보다 검사기를 먼저"
결정이 낳은 두 번째 배당이다.

**허브 문서 구조.** Transformer 4종은 공통 인프라를 공유한다. StateT 를 개념 허브로 두고
나머지 셋이 링크로 참조하니 같은 설명을 네 번 쓰지 않았다. 다만 **"M 은 문자열로 넘긴다"
절만은 4종 모두에 중복 배치**했다 — 링크로 미루기엔 너무 자주 밟는 함정이라고 판단했다.
중복을 없애는 것이 목적이 아니라 **읽는 사람이 밟을 지뢰를 없애는 것**이 목적이다.

**문서의 주장을 예제 안에서 실행 검증했다.** "섞으면 TypeError" 를 산문으로 쓰지 않고
`try/catch` 예제로 넣었다. 검사기가 그 블록을 실행하므로, 나중에 동작이 바뀌면 문서가
빨간색이 된다. **문서가 회귀 테스트가 됐다.**

## 2. 무엇을 잘못 가정했나

**`catchError` 가 인스턴스 메서드일 것이라 가정했다.** Task 에는 인스턴스 `catchError` 가
있어서(`index.js:1406`) EitherT 도 그럴 줄 알았다. 실제로는 **정적 메서드이고 인자 순서가
`(program, handler)`** 다(`index.js:2429`). 처음 호출을 `(handler, program)` 으로 써서
TypeError 를 받고 알았다. **같은 이름의 API 라도 타입마다 형태가 다를 수 있다** — 유추하지
말고 확인해야 한다.

**`CLAUDE.md` 를 신뢰할 수 있는 출처로 가정했다.** 회차 1의 "문서에 적힌 명령이 동작한다고
믿지 마라" 를 테스트 명령에만 적용하고 API 예제에는 적용하지 않았다. 프로젝트 자체 문서도
검증 대상이다. 이번엔 실행해보고 고쳤다.

## 3. 이 회차를 싸게 만들었을 것은

**`cd` 접두사를 그만 붙였어야 했다.** 하네스가 `cd` 실패 2회를 누적 집계하고 경고했다.
원인은 `cd` 자체가 아니라 **뒤따르는 명령의 실패가 `cd` 로 귀속**된 것이지만, 애초에 붙일
필요가 없었다 — **Bash 도구의 작업 디렉터리는 호출 간 유지된다.** 절대 경로를 쓰거나 그냥
생략하면 된다. 경고를 받고 나서야 뺐다.

**Transformer API 를 한 번에 조사했어야 했다.** `catchError` 인자 순서, 문자열/객체 차이,
WriterT monoid 변형을 세 번에 나눠 확인했다. Context 단계에서 4종의 전체 API 표를 한 번에
뽑았다면 왕복이 줄었다. **여러 형제 타입을 문서화할 때는 개별로 파지 말고 표를 먼저
만든다.**
