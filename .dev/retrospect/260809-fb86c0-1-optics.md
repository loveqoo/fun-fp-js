# 회고 — Optics 확장: Prism + Traversal (260809-fb86c0 · 회차 1, 작업 종료)

완료 조건 9개 전부 충족. 이 세션에서 **처음으로 문서·검증이 아니라 라이브러리 기능을 추가**한
작업이었다.

## 1. 무엇이 통했나

**기존 표현이 확장을 이미 감당하고 있었다.** `Lens` 가 van Laarhoven F-explicit
(`F => f => s => F.map(...)`)으로 되어 있어서, Prism 과 Traversal 을 **같은 표현으로** 쓸 수
있었다. `composeOptic` 도 기존 `composeLens` 와 로직이 동일하다 — F 를 모두에 주입한 뒤
concrete-F 레벨에서 합성한다. **종류가 다른 optic 끼리의 합성이 공짜로 나왔다.**

바꿔야 했던 것은 optic 이 아니라 **F 쪽**이었다:

| | 기존 | 추가 |
| --- | --- | --- |
| `_Identity` | `{of, map}` | `ap` (Traversal 이 결과를 모을 때) |
| `_Const` | 고정 `{of, map}` | **Monoid 로 매개변수화** + `ap` |

Const 를 Monoid 로 매개변수화한 것이 핵심이었다. **어떤 Monoid 를 주느냐가 읽기 방식을
정한다** — First 를 주면 `preview`, Array 를 주면 `toListOf`. 읽기 함수 셋이 같은 골격에서
나왔다.

**기존 Traversable 레지스트리를 그대로 물렸다.** `ArrayTraversable` 의 traverse 가
`applicative.of/map/ap` 세 가지만 호출하므로(`index.js:1031`), 내부 F 를 그 모양으로 맞추자
`traversed('array'|'maybe'|'either')` 가 한 줄로 끝났다. **새 Traversable 을 만들지 않았다.**

**하위 호환을 조건에 박아둔 것.** 완료 조건 4를 "기존 optics 테스트가 그대로 통과한다" 로
썼고, Planning 에서 `tests/optics.test.js:131` 이 에러 메시지를 **정확히 단언**하는 것을
발견했다. `composeLens` 를 단순 별칭으로 만들면 깨진다. 이름과 명사를 매개변수화해 기존
메시지를 보존했다:

```js
const _makeCompose = (name, noun) => (...optics) => { ... `${name}: argument ${i} must be ${noun}` ... };
const composeOptic = _makeCompose('composeOptic', 'an optic');
const composeLens  = _makeCompose('composeLens',  'a Lens');
```

계획에 이걸 "이 작업의 함정" 으로 적어둔 덕에 구현 중 잊지 않았다.

**구현을 일부러 깨뜨려 테스트를 검증했다.** Prism 의 매칭 분기를 없애고, `Const.ap` 의
Monoid 누적을 없애봤다. 둘 다 exit 1. **새로 쓴 테스트가 실제로 무언가를 지킨다**는 확인이다.

## 2. 무엇을 잘못 가정했나

**F 가 `{of, map, ap}` 를 갖추면 충분하다고 가정했다.** `traversed('array')` 를 처음 돌리자
`Traversable.traverse: first argument must be an Applicative` 로 깨졌다.
`index.js:406` 이 **`applicative[Symbols.Applicative]` 심볼을 검사**한다. 구조적 타이핑이
아니라 nominal 표식이 필요했다.

이건 이 라이브러리의 일관된 설계(심볼 기반 타입 식별)인데, optics 섹션의 내부 F 는 그 관례를
따르고 있지 않았다. `_asApplicative` 헬퍼로 Functor/Apply/Applicative 심볼을 붙여 해결했다.

→ **기존 코드에 물리려면 그 코드의 타입 식별 방식을 따라야 한다.** 시그니처만 맞추면 되는 게
   아니다.

**`review` 를 optic 함수에서 복원할 수 있다고 잠깐 생각했다.** 불가능하다 — van Laarhoven
인코딩은 `(a -> F a) -> s -> F s` 라서 `a -> s` 방향이 없다. 제대로 하려면 Choice/Tagged
profunctor 인코딩으로 바꿔야 하는데, 그건 `Lens` 표현 전체를 바꾸는 일이다.
`Prism` 이 `build` 를 심볼 프로퍼티로 들고 다니게 했다. **정직한 절충이고 문서에 이유를 적었다.**

## 3. 이 회차를 싸게 만들었을 것은

**`Symbols` 검사를 Context 단계에서 확인했으면** Execution 중 한 번의 왕복이 없었다.
`traverse` 구현(`index.js:1031`)은 읽었지만 **그 위의 strict 래퍼**(`index.js:405`)는 안 읽었다.
`checkAndSet` 이 모든 타입 클래스 메서드를 감싼다는 것은 `CLAUDE.md` 에도 적혀 있는 설계인데,
그걸 optics 에 연결짓지 못했다.
→ **기존 인스턴스를 재사용할 계획이면 그 인스턴스의 "검증 래퍼" 까지 읽어라.**

**문서를 쓰면서 API 가 한 번 더 다듬어졌다.** `view` 가 Traversal 에서 `undefined` 를 돌려주는
것을 문서 표를 만들다가 알아챘고, "`view` 는 Lens 전용" 을 명시하게 됐다. 처음부터 표로
정리하고 시작했으면 더 빨랐을 것이다.

## 남은 것 (다음 후보)

- **`Iso`** — 무손실 양방향 변환. `Prism` 의 `build` 표식 방식을 그대로 쓸 수 있어 가장 쉽다
- **`Optional`** — Lens + Prism (있을 수도 없을 수도 있는 단일 대상). `composeOptic(lens, prism)`
  로 이미 만들 수 있으므로 전용 생성자가 필요한지는 판단 필요
- **`Fold` / `Getter` / `Setter`** — 읽기·쓰기 전용. `toListOf`/`over` 로 이미 되므로
  타입 수준 구분이 목적일 때만 값어치가 있다
- `traversed` 가 쓸 수 있는 Traversable 이 array/maybe/either 셋뿐이다. Object 나 Map 이
  필요하면 `Traversable` 인스턴스를 먼저 추가해야 한다
