## 1. 무엇이 통했나

**계획대로 "실제 API 불일치" 를 먼저 봤다.** 미정의 헬퍼 46건이 숫자로는 크지만 값어치는

| 문서가 쓴 것 | 실제 |
| --- | --- |
| `maybe.getOrElse(x)` | **없다.** `Maybe.fold(onNothing, onJust, m)` 로 만든다 |

인스턴스가 실제로 가진 것은 `chain`, `map`, `isJust`/`isNothing`/`isRight`/`isLeft` 뿐이다.

`Either.md` 는 `.mapLeft(...)` 로 호출한다.

→ 고칠 방향이 자명해졌다. **문서 자신의 관례에 맞추면 된다** — 새 표현을 발명할 필요가 없다.

## 2. 무엇을 잘못 가정했나

**`docs/` 를 python 스크립트로 고치는 것은 파일 편집과 다르게 취급된다고 생각하지 않았다.**
`docs_readonly_bash` 로 차단됐다 — 하네스는 Bash 명령이 `docs/` 를 **변경할 수 있는지**
보고 막는다. Edit 도구든 스크립트든 같다. 직전 회고의 규칙 2(쓰기 클래스 선확인)를
파일 편집에만 적용하고 스크립트에는 적용하지 않은 탓이다.
→ **Execution 진입 시 그 회차가 건드릴 보호 경로의 `allow` 를 먼저 받아둔다.**

**진척이 생각보다 느렸다.** API 불일치 13건을 고쳤는데 실패는 3건만 줄었다(55 → 52).

**`grep` 으로 먼저 전수 조사했으면 더 빨랐다.** `.fold(` 와 `.getOrElse(` 를 문서 전체에서
grep 하니 위치가 7곳으로 즉시 나왔다. 검사기 실패 로그를 하나씩 따라가는 것보다 빨랐다.
**증상(실패 로그)이 아니라 패턴(문자열)으로 찾을 수 있으면 그쪽이 싸다.**

(a) 같은 문서 다른 블록에 정의가 있는 것(자동 보충 가능),
