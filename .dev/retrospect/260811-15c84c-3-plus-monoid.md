# 회차 3 회고 — 테스트가 "있다" 와 "잡는다" 는 다르다

작업 `260811-15c84c` 회차 3. 회차 2가 낸 `preview` 회귀를 고치고, `Plus` 에서 Monoid 를
유도해 `plus(maybe)`/`plus(array)` 로 등록했다.

**회귀는 잡혔다** — 리뷰어가 HEAD 대비 `preview` 18케이스를 대조해 **차이 0건**을 확인했다
(`[1,'a']`/`[null,1]`/`[undefined,1]`/`[NaN,1]`/Maybe 중첩/합성 optic 포함).

**그러나 위반 9건이 나왔고, 그중 둘은 이번에 내가 만든 검증 장치의 결함이었다.**

## 무엇이 통했나

### 사용자가 "이렇게 결정해도 되나" 라고 물은 것이 근거를 바꿨다

`Alt` 가 맞다는 것을 나는 실측(7/7 일치)으로만 말하고 있었다. 사용자가 **"근데 이렇게
결정해도 되나요? 다른 곳에선 어떻게 할지 모르겠군요"** 라고 물어 찾아보니, **Haskell `base`
가 이미 두 개의 별도 타입으로 나눠둔 것**이었다:

| | 동작 | 우리 |
| --- | --- | --- |
| `Monoid (Maybe a)` (`Semigroup a` 필요) | 안을 합친다 | `maybe(first)` |
| `newtype First a = First (Maybe a)` | 안을 안 본다 | **없었다** → `plus(maybe)` |

그리고 `lens` 의 `preview` 는 `First` 를 쓴다. **즉 임의 결정이 아니라 표준이 혼동을 막으려고
분리해둔 것을 우리가 하나만 갖고 있었던 것이다.** 리뷰어가 이 네 인용을 전부 사실로 확인했다.

**실측이 "무엇이 다른가" 를 말하고, 참조 구현이 "왜 달라야 하는가" 를 말한다.** 나는 앞의
것만 갖고 결정하려 했다.

### 뮤테이션 테스트가 자기기만을 갈랐다

회차 2의 교훈은 "본체에 테스트를 써라" 였고, 이번에 10건을 썼다. **그런데 핵심 하나가
아무것도 고정하지 못했다.**

리뷰어가 `binaryTypeError` 의 `'any'` 분기를 **통째로 지웠는데 38 파일 전부 초록**이었다.
원인은 내 어서션이 부분 문자열이어서다:

```javascript
assertThrowsWith(() => Semigroup.of('first').concat(1, 'a'), 'must be the same type');
// HEAD 메시지: "...arguments must be the same type and match object"  ← 이것도 포함한다
```

**개수를 세는 것으로는 안 걸린다.** 회차 2의 교훈("테스트 0건")을 개수로 이해하고 품질로
이해하지 않았다.

## 무엇을 잘못 가정했나

### 1. 검증 도구를 만든 것으로 안심하고, 도구를 검증하지 않았다

Scaffolding 에서 `tests/baseline.js` 를 만들었다 — 회차 1·2가 놓친 회귀를 잡으려고.
**그런데 그 도구가 이 라이브러리의 핵심 구분을 숨겼다.**

```
[Just(1), Nothing]         -> [{"value":1,"_typeName":"Maybe"},{"_typeName":"Maybe"}]
[Just(1), Just(undefined)] -> [{"value":1,"_typeName":"Maybe"},{"_typeName":"Maybe"}]   동일
Right(2) / Left(2)         -> 둘 다 {"value":2,"_typeName":"Either"}                     동일
```

`render` 가 **최상위** 컨테이너만 풀고 안쪽은 `JSON.stringify` 에 넘겼다.
`Nothing`/`Just(undefined)`, `Left`/`Right`, `NaN`/`null` 이 전부 붕괴한다.

**차이를 숨기는 대조 도구는 없는 것보다 나쁘다.** 있으면 봤다고 착각하기 때문이다.

### 2. "차이 3건" 이라 보고했는데 7건이었다

계획서 Verification 1번을 "남는 차이가 `view` 3건" 이라 썼다. **"3건" 은 내가 지운 테스트의
개수였지 동작 차이의 개수가 아니었다.** 고친 도구로 다시 재니 `view` 다중 대상에서 7건
(`3→1`, `"a"→1`, `"b"→"a"`, `1→null`, `1→undefined`, `[2]→[1]`, `{z:2}→{z:1}`).

**내가 확인한 표본을 모집단으로 착각했다.** 격자를 넓히는 데 드는 비용은 거의 0이었다.

### 3. "규칙이 낫다" 고 주장하면서 규칙을 안 만들었다

계획서가 `plus(array)` 등록을 **"`Plus` 가 있는 타입은 전부 Monoid 를 얻는다는 규칙이
하나뿐인 특례보다 낫다"** 로 정당화했다. 그런데 **그 규칙은 코드 어디에도 없다** — 손으로
쓴 클래스 2개만 있다. `Plus` 를 새로 등록하는 다음 사람은 또 손으로 써야 하고, 안 써도
아무것도 알려주지 않는다.

리뷰어가 `Plus` 생성자에서 유도하는 프로토타입을 만들어 **38 파일 통과 + 12줄 감소**를
보였다. 내 근거가 옳았고 구현이 그 근거를 배신했다.

그 결과 `plus(array)` 는 `Monoid.of('array')` 와 **관측 차이 0**(입력 12쌍 + `empty()` 전수)
이면서 소비자도 0인 순수 중복이 됐다 — 유형 1을 레지스트리 안에서 저질렀다.

### 4. 새로 만든 것을 또 TS 층에서 가뒀다

`plus(maybe)`/`plus(array)` 가 `MonoidInstances` 에 없다. 리뷰어가 `@ts-expect-error`
프로브로 확인했다. **회차 1 리뷰 #3과 같은 실패다** — 그때는 키를 없애서 "해소" 됐고,
이번엔 다시 만들면서 같은 곳을 빠뜨렸다. `npm test` 의 `tsc` 가 초록인 이유는 **d.ts 가
새 키를 모르는 것을 아무도 검사하지 않기 때문**이다.

## 이 회차를 싸게 만들었을 것

### ① 도구를 만들자마자 도구의 실패 사례로 시험했어야 했다

`tests/baseline.js` 를 만든 직후에 "이 도구가 놓칠 수 있는 것은?" 을 물었으면 5분이었다.
`Just(undefined)` 하나만 넣어봤어도 나왔다. **회귀를 잡는 도구를 만들 때는 그 도구가
못 잡는 회귀를 먼저 나열해야 한다.**

### ② 리뷰어의 프로토타입 방식을 내가 먼저 썼어야 했다

리뷰어는 "규칙으로 올릴 수 있나" 를 **실제로 고쳐서 테스트를 돌려** 답했다. 나는 "선례가
없다"(타입 클래스 정적 팩토리)에서 멈췄다. **선례가 없다는 것은 못 한다는 뜻이 아니다** —
회차 2에서 배운 "없는 것에는 이유가 있을 수 있다" 의 반대편 함정이다. 이유를 찾아보고
없으면 만들면 된다.

### ③ 어서션을 쓸 때 "이게 HEAD 에서도 통과하나" 를 물었어야 했다

한 줄이면 됐다. `'...and match object'.includes('must be the same type')` → `true`.
**테스트를 쓰는 순간이 그 테스트의 가치를 확인할 가장 싼 시점이다.**
