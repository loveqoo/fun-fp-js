검색 키: `Profunctor` `promap` `Strong` `Choice` `Wander` `재사용` `근거 없는 판단`

# 회고 — dimap 위임 + 미채택 근거 기록 (260811-6a3349 · 회차 1, 작업 종료)

완료 조건 6개 전부 충족. 코드 변경은 세 줄이지만 **얻은 것은 판단 방식**이다.

## 1. 무엇이 통했나

**사용자가 "검색해서 데이터를 보고 말하라" 고 못 박은 것이 결정적이었다.**
나는 "커스텀 profunctor 를 등록할 실사용 시나리오가 잘 떠오르지 않는다" 로 결론을 냈는데,
검색해보니 **실사용 시나리오는 실재했다**:

- **indexed optics** — 위치를 주는 traversal (`itoListOf itraversed "foobar"` →
  `[(0,'f'),(1,'o'),...]`)
- **실패 이유를 돌려주는 Prism**

"떠오르지 않는다" 는 내 무지였지 데이터가 아니었다.

**그런데 데이터가 결론을 바꾸지는 않았다 — 근거를 바꿨다.** 검색이 보여준 것:

| 발견 | 함의 |
| --- | --- |
| JS/TS 선례 만장일치 내부화 (optika "Internals", monocle-ts "only used internally") | 이 판이 이미 답을 냈다 |
| indexed optics 는 `Indexed`/`StarI`/`ForgetI` + `itraversed` 를 요구 | **Strong/Choice/Wander 만 올려도 그 용도가 안 열린다** |
| well-typed/optics 의 내부화 이유는 **에러 메시지 품질** | 타입 추론 문제라 **JS 에는 해당 없음** |

세 번째가 특히 값졌다. 이건 **내가 앞서 저지른 실수(Haskell 의 Wander 난이도를 JS 로 옮김)의
정확한 거울상**이다 — 이번엔 반대 방향으로 같은 실수를 할 뻔했다. 남의 라이브러리 결정을
가져올 때는 **그 결정의 이유가 우리에게도 성립하는지**를 따로 봐야 한다.

**결론이 같아도 근거가 다르면 다른 결론이다.** 처음엔 "용도가 없다"(틀림), 나중엔
"용도는 있으나 이 셋으로는 안 열리고, 선례가 만장일치이며, 흔한 반대 논거는 우리에게 무효".
두 번째만 다음 사람이 재검토할 수 있는 형태다.

**내부 리팩터링을 테스트 무수정으로 통과시킨 것.** 완료 조건 4를 "기존 59개가 그대로
통과한다" 로 못 박아뒀다. 동작이 바뀌면 안 되는 변경이므로 이게 유일하게 의미 있는 검증이었다.

## 2. 무엇을 잘못 가정했나

**`Traversable` 은 재사용해놓고 `Profunctor` 는 존재 여부도 안 봤다.** 같은 작업 안에서
한쪽은 레지스트리를 뒤졌고 다른 쪽은 안 뒤졌다. 일관성 없는 조사였다.

더 나쁜 건 **계획서에 "왜 안 쓰는가" 가 한 줄도 없었다**는 점이다. 안 쓰기로 한 게 아니라
**생각 자체를 안 했다.** 사용자가 묻지 않았으면 그대로 남았을 것이다.

→ **규칙: 새 개념을 도입할 때 같은 이름의 것이 이미 있는지 먼저 grep 하고, 안 쓰기로 했으면
   그 이유를 계획에 적어라.** `Profunctor`, `Strong`, `Choice` 를 grep 하는 데 5초였다.

**"떠오르지 않는다" 를 근거로 썼다.** 이건 데이터가 아니라 내 지식의 한계다.
→ **규칙: 실사용 시나리오의 유무를 주장하려면 찾아본 뒤에 말하라.** 안 찾아봤으면
   "모른다" 가 정직한 답이다.

## 3. 이 회차를 싸게 만들었을 것은

**Prism/Traversal 작업의 Context 단계에서 `Profunctor` 를 grep 했으면** 이 회차가 통째로
없었다. 그때 `traversed` 를 위해 `Traversable.types` 를 열어봤으면서 옆에 있는
`Profunctor.types` 는 안 봤다.

**미채택 근거를 계획서에 적는 습관이 없었다.** 지금까지 계획서의 "범위 밖" 절은 *무엇을*
안 하는지만 적었지 *왜* 안 하는지는 적지 않았다. 이번엔 근거까지 적었고, 그게
`CLAUDE.md` 로 옮겨져 다음 사람이 같은 질문을 하지 않게 됐다.
→ **"범위 밖" 에는 무엇과 함께 왜를 적는다.** 특히 "기존 자산을 안 쓴다" 는 결정은 반드시.

## 남은 것

- `Strong`/`Choice`/`Wander` 타입 클래스 — **사용자가 커스텀 profunctor 등록을 실제로
  요구할 때** 추가한다. 그때 `Tagged` 의 strict 검사 문제(값 profunctor 를 거부)도 함께 풀어야
  한다. 조건과 근거를 `CLAUDE.md` 에 적어뒀다
- indexed optics — 별도 profunctor 계열이 필요한 큰 작업
- `Optional`/`Fold`/`Getter`/`Setter` — 기존 연산으로 이미 되므로 타입 수준 구분이 목적일 때만
