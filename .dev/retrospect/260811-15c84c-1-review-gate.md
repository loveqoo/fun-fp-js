## 무엇을 잘못 가정했나

### 1. "교훈을 배웠으니 같은 실수는 안 한다" — 형태만 바꿔서 했다

이 세션에서 배운 것: **만들어놓고 아무도 못 쓰게 가둠**(사설 Applicative 2개, 사설 Monoid
3개, bare export 11개). 사용자가 네 번 지적해서 겨우 고쳐진 것이다.

그리고 이번 회차 Context 단계에서 `CLAUDE.md` 에 이걸 넣었다:

```
Profunctor ──> Strong ──┐
           └──> Choice ──┴──> Wander      (optics 가 쓴다)
```

**코드에 0건이다.** `Profunctor.types` 는 `['FunctionProfunctor', 'function']` 뿐이고
`Strong`/`Choice`/`Wander` 는 export 되지 않는다(실행으로 확인). 게다가 **내 계획서
106줄이 "범위 밖 — Strong/Choice/Wander 타입 클래스" 라고 적어놨다.** 계획이 범위 밖이라
선언한 것을 문서에만 구현했다.

이건 배운 실수의 **거울상**이다 — 저번엔 코드에만 만들고 문서에 안 냈고, 이번엔 문서에만
만들고 코드에 없다. 공통 뿌리는 하나다: **"있어야 할 것" 을 "있는 것" 으로 쓴다.**

가장 나쁜 점은 `CLAUDE.md` 가 **항상 로드된다**는 것이다. 회차를 넘겼으면 다음 Selection
부터 오염된 상태로 시작했다. Compounding 의 쓰기 권한에 `context` 가 있어 이 단계에서
고쳤다.

**교훈을 산문으로 아는 것과 그 순간에 적용하는 것은 다른 능력이다.** 그래서 게이트가
필요하다 — 알면서도 하기 때문이다.

### 2. "사설을 레지스트리로 옮기면 사용자가 바꿔 낄 수 있다" — 코드가 그렇지 않다

`index.js:2315` 에 내가 쓴 주석:

> 모으기에 쓸 Monoid 는 레지스트리에서 꺼낸다 — 사설로 만들면 사용자가 바꿔 끼울 수 없다.

리뷰어가 `Monoid.types['maybe-first']` 를 갈아끼우고 실행했다. **결과가 안 바뀐다.**
`const _firstM = Monoid.of('maybe-first')` 가 **모듈 로드 시점에 인스턴스를 상수로 캡처**
하기 때문이다. 사용자 관점에서 사설이었을 때와 달라진 게 없다.

즉 **박힌 위치를 사설 리터럴에서 모듈 상수로 옮겼을 뿐이고, 주석은 있지도 않은 이득을
주장한다.** 리팩터링의 목적을 주석에 썼는데 그 목적이 코드에 없었다.

**신호: "이제 사용자가 ~할 수 있다" 를 쓸 때는 그 문장을 실행으로 확인하라.** 확인
못 하면 쓰지 마라.

### 3. "레지스트리에 있는지 봤다" — 봤는데 옆칸을 못 봤다

판단 규칙 1번("만들기 전에 레지스트리를 grep 한다")을 이번엔 지켰다. `Semigroup.types` 를
조회해 `first`/`last` 가 이미 있는 것을 확인했고, 그것들이 primitive 전용이라 Maybe 에
못 쓴다는 것까지 실행으로 검증했다.

그런데 **`MaybeAlt` 를 못 봤다.** 내가 새로 쓴 `(a,b) => a.isJust() ? a : b` 는
`index.js:1123` 의 `MaybeAlt: (a,b) => a.isNothing() ? b : a` 와 **4개 입력 전수에서
객체 동일성까지 같다.** `MaybePlus.zero` 도 `Maybe.Nothing` 으로 이미 같다.

grep 하긴 했는데 **`Monoid.types`·`Semigroup.types` 만 봤다.** 같은 연산이 `Alt`/`Plus`
라는 **다른 타입 클래스 이름**으로 등록돼 있을 가능성을 안 봤다.

**신호: 레지스트리 조회는 "이 이름이 있나" 가 아니라 "이 연산이 있나" 다.**
`concat` 을 찾을 땐 `Semigroup` 만이 아니라 `Alt`(같은 결합 연산), `empty` 를 찾을 땐
`Monoid` 만이 아니라 `Plus`(같은 항등원)를 봐야 한다. 저장소가 이미 그렇게 파생한다 —
`MaybePlus` 가 `Alt.types.MaybeAlt` 를 받아 만들어진다.

### 4. 절차 — `stages.json` 을 Context 에서 고쳤다

구조 변경은 Scaffolding 의 일인데 Context 에서 했다. 게이트가 **경로 클래스**만 보고
두 단계 모두 `context` 를 쓸 수 있어 안 걸렸다. 결과는 옳아서(진단 4건 → 0건) 되돌리지
않았고 규칙으로 남겼다(`.dev/learning/260811-15c84c-1-judgment-rules.md` 4번).

## 이 회차를 싸게 만들었을 것

### ① 리뷰 노드를 **첫 optics 회차**에 세웠어야 했다

지금 갚고 있는 부채 — 사설 딕셔너리 5건, bare export 11개, 잘못 인용한 선례 3건 — 는
전부 **리뷰 없이 진행한 두 회차**에서 생겼다. 사용자가 네 번 지적해 겨우 드러났다.
게이트를 나중에 세우면 게이트가 **자기 앞의 부채를 청구서로 받는다.** 실제로 이번
리뷰 6건 중 3건이 그렇다.

### ② `foldMap(monoid, optic, s)` 를 **먼저** 냈어야 했다

Monoid 를 사설에서 레지스트리로 옮기는 작업의 목적은 "사용자가 고를 수 있게" 였다.
그런데 **고르는 입구를 안 냈다.** 입구가 `foldMap` 이다. 그것부터 냈으면:

- 주석의 주장이 코드로 증명됐을 것이다 (실수 2 방지)
- `_firstM`/`_arrayM` 상수 캡처가 애초에 안 생겼을 것이다
- `toList` 가 `foldMap(Monoid.of('array'), ...)` 의 특수 경우로 자연히 정리됐을 것이다

**"내부를 레지스트리로 바꾼다" 는 그 자체로 사용자 가치가 0이다. 값은 입구에서 나온다.**
입구 없는 내부 교체는 리팩터링이 아니라 코드 이동이다.

### ③ 동작 변경을 **테스트로 먼저** 잡았어야 했다

`view` 3건이 조용히 바뀐 것은 세 경우에 테스트가 없었기 때문이다. `_lastMonoid` 를
지우기 **전에** 지금 동작을 기록하는 테스트를 3줄 썼으면, 지우는 순간 빨간불이 켜지고
**"바꿀 것인가" 가 결정으로 올라왔을 것이다.** 지금은 부수 효과로 일어나 아무 데도
안 적혔다.

POLICY 4번("중요한 기능은 테스트로 먼저 동작을 확인한다")이 이걸 말하는데, 나는
"내부 교체니까 해당 없음" 으로 읽었다. **내부 교체인지 아닌지가 바로 검증 대상이었다.**
